# Eight-byte C owner events with rehash — unselected

This experiment is based on the exact selected source `baseline.rs`, SHA-256 `6e12627e96f0a0433e567413ccacc1a5d7fdf2de8f4781a3f826c260499783dd`. Candidate `candidate.rs` SHA-256 is `6eaa6e4796a02a4004cf9d2f10436490305cc0d857dc23e35b9f1eb674f1377e`. It removes the stored u64 hash from each name/group event, reducing the event payload from 16 to 8 bytes, and recomputes `name_hash(name)` in the owner after reconstructing the exact name. Parsing still computes the same hash to select the owner; exact name bytes and collision chains, long-name sentinel, fallback and bitsets remain unchanged. The existing fused scanner and `name_hash` must agree for each valid encoded name; this was tested in the prior `c-fused-namehash` property suite. Long names are reparsed, as in the selected source. No data recognition or cached answers are used.

Validation on macOS ARM: `experiments/c-fused-namehash/reference.py --source experiments/c-short-event-rehash/candidate.rs --seeds 24` passed 120 mixed CSV reference comparisons over five worker counts. The adapted `edge.py` passed 20 comparisons across long names, sentinel boundaries, forced owner routing/full-hash collision and pre-output fallback; its full-hash variant forces both owner routing and reduction hashes to zero. Two randomized 15-pair full seed-1 batches plus warmups produced all 64 published output hashes. No independent code review, x86 AVX2 check or official score was attempted because of the slower screen.

Uninstrumented native ARM timings, baseline versus candidate: batch one median wall 79.291 vs 86.729 ms and CPU 471.477 vs 524.397 ms; batch two median wall 76.865 vs 82.452 ms and CPU 460.098 vs 520.080 ms. Median native process RSS was 270.69 vs 242.62 MiB and 270.44 vs 243.11 MiB. These are shared-host, nonofficial results; raw samples are `arm-report.json` and `arm-repeat.json`. The clear CPU and wall regression does not justify promotion under speed-first direction despite lower memory.

A separate 15-pair phase-instrumented comparison passed all 32 full hashes. It measured parser 38.426 vs 36.658 ms, reducer 29.854 vs 38.840 ms, and total 73.040 vs 80.833 ms baseline versus candidate. These timers and stderr writes change the measured program and cannot be treated as production benchmarks; they suggest the extra reducer hashing dominates the event-size savings. Raw samples are `arm-phase-paired.json`, and `profile-candidate.rs` and `paired-phase.py` reproduce the measurements using the instrumented baseline in `../c-current-phase-profile/profile.rs`. The earlier unpaired instrumented candidate run is `arm-phase-report.json`.

To reproduce, generate full seed-1 data separately; no datasets are included. Compile `baseline.rs` and `candidate.rs` identically with `rustc --edition=2021 -O -C lto=fat -C codegen-units=1 -C panic=abort`; then run `python3 experiments/c-nameowned/compare.py --baseline /path/to/base --variant /path/to/candidate --data /path/to/full-c --runs 15 --report /tmp/c-compare.json`. Use a compatible x86-64-v3 flag only on capable x86. Confirm actual x86 and all tests before any promotion. No Mac Docker was used.
