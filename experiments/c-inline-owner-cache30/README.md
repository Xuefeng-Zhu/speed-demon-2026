# Exact inline owner-row cache screen — unselected

Baseline is the current two-lane C source, SHA-256 `8249f318e26050cc1a12f2be091344bf431ceb862665a3312bb29a92e140057d`. Both experiments keep owner routing, exact dictionary collision handling and the original long-file/group fallback. On 8–16-byte raw names, their row cache stores the first and last eight bytes, whose union covers the entire name; length is stored and must match. Longer and shorter names still use exact existing row-slice comparison. Rows that cannot fit below the reserved `u32::MAX` cache sentinel are not cached. On full-hash collision, unequal names cannot produce a hit because the inline bytes are compared exactly; this is not a probabilistic hash-only shortcut.

`candidate.rs` SHA-256 `fb870b9681a1cbec7d1c4a9ddd3a8e425c392f621b2d2d3506007bd0850afdd0` uses a 32-byte cache slot including full hash. `candidate24.rs` SHA-256 `f1754ee313a465dd75cd2b38da770eedf1338715bb37256bb3e9c8ee0c17ad75` uses a 24-byte slot: short hits use exact inline bytes without storing the full hash; long hits still compare the hash then exact bytes. It relies on the existing invariant that equal raw names have equal parser hashes and hence the same owner and cache index. Increasing per-owner cache memory can erase the saved pointer dependency. Neither candidate changes selected code or has x86/official cgroup evidence.

Both candidates passed an optimized overflow/debug-asserted independent OwnerDict model: 8 million (name,group) operations across forced same-hash promotions, same-slot replacements and 1–257 groups, plus direct 0–64-byte exact-inline equality/single-byte mutation tests. Both passed 12 mixed official-reference corpora × five worker counts. The true Linux x86 AVX2 path, guard pages, >4 GiB input and hidden-data cgroup maximum were not tested. The temporary test files combine each candidate with `test-tail.rs` or `test-tail24.rs` and compile `rustc --edition=2021 --test -O -C overflow-checks=yes -C debug-assertions=yes`.

On the shared native ARM Mac with no overlapping benchmark, the 32-byte candidate's randomized 11- and 15-pair full-public-data median walls were 0.071894 vs baseline 0.071162 seconds, then 0.071313 vs 0.071096 seconds; CPU medians were 0.393080 vs 0.397730, then 0.395034 vs 0.396651 seconds. Median process RSS was about 6 MiB higher. The 24-byte candidate's corresponding walls were 0.065228 vs 0.064683 seconds and 0.064049 vs 0.064622 seconds; CPU was 0.391607 vs 0.399906 and 0.391216 vs 0.396550 seconds; native median RSS was 2.6–4.3 MiB higher. Every warmup and timed output across both screens matched the public full-seed hash. These small, inconsistent native differences do not establish an x86 speed win; retain the selected C source. Raw paired measurements are in the four `arm-*.json` files. No Docker was run on the Mac.
