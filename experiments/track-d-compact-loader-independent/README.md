# Independent compact-loader staging review

This review targets exact candidate SHA-256 `d74c9104ddb3ce661e1e597276c2bb9da621a73bbe6846cd82f901de719c1d64` against exact selected hybrid baseline `671c639be3400209e83e080dfb54947affd30ca71dc34ec17804d24d70292d9c`. It does not establish target speed or a complete parent-cgroup memory bound.

For `n <= 2^21`, each bin stores the tail and head in separate 21-bit fields and an 11-bit weight tag. Tags 0 through 2046 retain the complete weight; tag 2047 takes the next weight from that bin's sequential `overflow` vector. Each `edges` traversal restarts its own ordinal at zero and visits the packed entries in their insertion order. Forward and reverse records are inserted into separate bins, so each direction has its own side stream. The two CSR passes traverse each parser's bin in the same order; the first uses only tail fields, and the second decodes all fields and scatters with the existing per-block cursor. When `n > 2^21`, `plain` stores the original `(u32,u32,u32)` tuples. The search and final CSR encoding are unchanged. Every builder thread owns disjoint CSR slices and reads the completed bins immutably. Static review found no concrete encoding, ordinal, edge-order, or ownership defect under the input contract.

`python3 experiments/track-d-compact-loader-independent/run.py` hash-checks the exact candidate, appends a separate Rust unit-test module to a temporary copy, and compiles with `-O`, overflow checks, and debug assertions. It passed three independent tests: 750,000 mixed append operations over seven bins, both storage modes and five initial capacities; 200,000 all-wide-weight records; and plain-mode IDs above the 21-bit packing limit. Cases include weights 0, 2046, 2047, 2048 and `u32::MAX`, highest encodable node IDs, random values, repeated decode traversals, empty bins, and independent source-only iteration. These unit tests do not replace the author's independent full CSR multiset, graph-oracle, or target-x86 tests.

The format can reduce the staging payload for small weights, but it is **not** universally 33% smaller. When every edge weight needs overflow storage, packed plus side-stream logical payload is 8 + 4 = 12 bytes per directed staged edge, equal to the original three-u32 tuple on the target ABI, before extra Vec headers, capacity slack and allocator overhead. At 12 parser threads and 5,000,000 input edges, initial requested capacities for the 288 staging vectors are 90,146,304 bytes in the packed representation versus 135,219,456 bytes in the tuple representation; side streams begin empty and grow independently. The 10,000,000 forward/reverse entries logically require 80,000,000 packed bytes plus as many as 40,000,000 overflow bytes. `Vec` growth, reallocation transients, freed-page retention, other loader/query state, and kernel/cache charges remain input- and implementation-dependent. No worst-case 8 GiB parent-cgroup proof follows from this analysis. No x86 or official measurements were performed, and no Docker ran on the Mac.
