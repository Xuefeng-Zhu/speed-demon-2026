# Eager degree-two corridor propagation (unselected)

This isolated experiment is based on the selected batch16 Track D implementation: `baseline.rs` SHA-256 `7fd333be25133a78264cb4b84441de46d4c8bcbfd73914af23761f23d8c47f17`, `candidate.rs` SHA-256 `18edf019759e4ade3fdc4aee09355572993ae4e6fe960a8b3f03e10fef0761b4`. After a strict distance improvement across `u -> v`, it eagerly propagates through at most 16 vertices whose outgoing row contains exactly two edges and exactly one returns to the predecessor, then uses the original queue. It records each intermediate distance and opposite-side meeting; the return edge cannot improve its predecessor with nonnegative weights. It conservatively enqueues all ambiguous rows, handles u32 cutoff and forces the original exact wide fallback on exhausted pools. This is distinct from the earlier degree-one eager chain and precomputed/on-demand shortcut experiments. It does not change selected source.

The stopping-bound/frontier argument is **not independently proven**: eager out-of-order propagation must preserve bidirectional termination even with stale queued entries, repeated improvements, zero-weight cycles and fallback. Observed test results are finite, not proof. No x86, official board or cgroup result is claimed.

`python3 experiments/track-d-eager-corridor19/verify.py` built overflow/debug-checked candidates for each combination of pool cap 0, 1, 2, 16 and 65,536 and worker count 1 and 7. Each binary passed 16,000 independent random Dijkstra queries, 36,864 exhaustive small-graph answers, u32 cutoff and unreachable/self cases, and 7,308 answers across 36 independently generated road-like directed multigraphs with chains, zero weights, maximum weights, self loops, reverse edges and duplicates. `coverage.py` built a separate instrumented candidate, verified forward/reverse/self answers on a 120-node two-way path and confirmed 224 actual eager steps. These checks do not include full-size max-weight chain, independent formal review, every graph, or hidden data.

On a shared native ARM Mac, after one warmup per executable, nine randomized full-seed pairs all matched the organizer's `distances.txt` SHA-256 `a23dbdf0a3e49cc8901310a9ee1dc6a9a569a85297b6da75c2a7002cb2ed277e`. Median wall was **0.303648 s candidate versus 0.246514 s baseline** (23.2% slower); median process CPU was **2.167457 versus 1.785379 s** (21.4% higher); maximum process RSS was 585,383,936 versus 583,401,472 bytes. The independently generated graph and query hashes were checked against the official seed-1 spec before timing. All raw runs, compiler flags and hashes are in `arm-full.json`. Native Mac measurements are not target x86, official scoring or parent-cgroup measurements. Given this initial regression, the candidate remains unselected; no Mac Docker was run.

For a controlled repeat on generated public seed-1 input, `python3 experiments/track-d-eager-corridor19/compare.py --data /path/to/data --build-dir /tmp/d-corridor-build --report /tmp/d-corridor-report.json --runs 9`; the comparator verifies each output hash. The checked-in scripts and report contain no datasets or credentials.
