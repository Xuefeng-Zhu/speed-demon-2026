# Conditional requested-payload accounting

This is a planning envelope, **not a parent-cgroup proof**. For official full dimensions n=1,740,512, m=5,000,000, at most 12 workers, 12-byte `Edge` tuples, and 2 MiB per worker stack, start with the earlier hybrid's deliberately cumulative listed-payload estimate of 2,265,040,180 bytes (`../track-d-indexed-memory-bound/README.md`). Replace its 750,438,912-byte conditional old geometric-bucket allowance with the fast fixed logical bucket requests (135,219,456 bytes) plus the exact two-pass retry's requested edge buckets (120,000,000 bytes). Conservatively add one full input-buffer pass (135,000,411 bytes) and another 12 x 2 MiB of worker stacks (25,165,824 bytes). The listed sum is 1,929,986,959 bytes, about 1.80 GiB.

This deliberately adds both attempts even though the fast attempt's Rust objects are dropped before retry, to allow for some retained pages. It is neither a worst-case allocator-footprint guarantee nor an 8 GiB cgroup bound: `Vec::try_reserve_exact` exposes any extra capacity only after allocation; allocator fragmentation/retention beyond the allowances, actual stack/TLS/runtime, kernel page tables and other cgroup charges remain unspecified. Rust `Vec` guarantees at least the requested capacity, not a strict physical upper bound. The 320 MiB fast ledger covers cumulative requested input buffers, edge buckets and outer bucket vectors, and charges reported overcapacity after allocation; it does not cover fixed join/result metadata, CSR/search allocations, exact retry, page cache or any kernel/harness charges. Neither finite stress nor this arithmetic establishes correctness or safety for every holdout.
