# Indexed radix queues for D u32 cutoff (unselected)

This isolated prototype replaces each dynamically growing radix bucket vector in `../track-d-u32-cutoff-rebased/candidate.rs` with intrusive per-vertex doubly linked lists and fixed bucket heads. The baseline SHA-256 is `5c07ea85035e37157f77c66ccd06d86cefd022cc42311aa95497f78dc4a6d451`; candidate SHA-256 is `5e0caa893af2ae87c65cbb696f902c89c2c8fe30b06d97bfd4e220eedeed885c`. It is not selected or submitted. No Docker was run on the Mac.

Each direction holds at most one queued entry per vertex. Before a strict distance decrease, the old entry is unlinked and its replacement inserted; keys remain monotone. A bucket is redistributed by finding its minimum then unlinking and reinserting its entries; `top`, `push`, `pop`, `remove` and `clear` allocate no dynamic storage. Each heap allocates one `[u32; 2]` link pair per vertex and fixed 65 bucket heads. Thread count is capped at 12, and each touched vector reserves n u32 entries, so the query-time application data structures have a calculable payload instead of accumulating input-dependent per-bucket Vec capacities. This is a prototype, not a formal independent proof of correctness or the parent cgroup memory bound.

For full n=1,740,512 and 12 threads, if every worker retains both narrow and fallback-wide states, 24n bytes of distance arrays, 32n of directional links and 8n of touched entries per worker total 1,336,713,216 bytes. The two packed CSRs request 93,924,104 bytes. A deliberately conservative loader-plus-query accounting, under explicit assumptions that actual Rust Vec growth remains geometric and allocator reservations follow requested capacity, totals roughly 2.574 GB of listed payloads including all parser bucket growth, file cache and read buffers, CSR/cursors and four sets of 2 MiB stacks. This leaves substantial headroom but **does not prove the cgroup stays below 8 GiB**: `Vec` does not normatively cap allocator over-allocation; kernel/cgroup, allocator fragmentation and retained pages, runtime, harness and sandbox costs require separate bounds or controlled allocation. The accounted query and loading phases do not all necessarily peak together.

Overflow/debug-enabled ARM build passed the independent `../track-d-balanced-frontier/oracle.py` (16,000 randomized answers), `exhaustive.py` (36,864 all-pairs answers on 4,096 graphs), `../track-d-packed32-adj/boundaries.py` (n=2^21 and 2^21+1, max ID and wide weight), and `../track-d-u32-fallback/thresholds.py` (cutoff-1, cutoff, cutoff+1, zero/unreachable/self). `python3 experiments/track-d-indexed-radix/run-property.py` passed one million mixed queue insert/decrease/pop/clear operations against a `BTreeSet` model under debug and overflow checks. The prototype has not had complete full-seed or independent code review, Linux x86 performance, true cgroup, or holdout testing.

One 15-pair randomized native ARM sample batch, with warmups and all 32 public sample output hashes correct, measured baseline median wall **0.019058 s**, CPU **0.092508 s**, peak process RSS **38,092,800 B**, versus candidate **0.030949 s**, CPU **0.156653 s**, RSS **60,456,960 B**. This is approximately 62% slower wall in a short shared-host sample, not a full-scale or official comparison. The poor preliminary speed result prevents promotion under the speed-first goal. Raw observations and compile flags are in `sample-arm.json`; `compare.py` reproduces paired testing and accepts an explicit expected output hash.
