# Single-pass direct atomic name slots — unselected

The baseline is exact selected fused owner SHA-256 `6e12627e96f0a0433e567413ccacc1a5d7fdf2de8f4781a3f826c260499783dd`. The candidate is `021b2c9b83c7c8e7bac79016c32c844986675f4ae488374ab2f9c121c7fc0560`.

For compact input with at most 256 total groups, each parser hashes a name and looks up one of 1,048,576 direct atomic slots. A successful slot claim publishes an immutable borrowed name with four inline atomic group words. Concurrent repeated names update the same group bit atomically; distinct names sharing a slot use an exact independently randomized sharded dictionary protected by locks. This removes the selected path's buffered event distribution and second reduction phase. Inputs with more than 256 total groups use the original selected owner path; files failing the existing packed-size gate use the original selected sharded fallback. Claimed nodes persist until process exit. Directory payload is 8 MiB on a 64-bit host and at most one node per slot is retained, plus allocator overhead. Collision dictionaries are data-dependent; the fixed directory is not a bound on overall memory or runtime.

This is related to `experiments/c-fastslot`, which used 262,144 slots and separately allocated group-bit arrays on an older parser; that earlier design **regressed on native x86**. Its exact regression magnitude was not supplied. This variant changes slot count, node layout, collision hashing and parser, so the earlier result neither proves nor rules out a target win.

The exact candidate passed 24 mixed reference corpora across five worker counts; 27 concurrent reference runs with normal, constant-hash and single-slot routing at 2/8/32 workers; 20 lookup/group reference checks through 17,576 country codes; 20 long-name/forced-fallback cases; concurrent publication/bit-transition checks at 1/2/8/32 workers; and a forced one-slot, one-group 50,000-distinct-name/8-worker oracle. The >256-group original-owner fallback was checked with a 17,576-code and 17,576-distinct-name fixture at 32 workers. Native ARM peak RSS for that finite fixture was 84,557,824 bytes candidate and 80,527,360 baseline; neither is a worst-case bound or cgroup peak. The actual >4-GiB parse, independent unsafe/concurrency review, Linux AVX2 and official gates are not complete.

One 15-pair shared ARM full-seed screen yielded candidate/baseline median wall 0.09055/0.09527 s, CPU 0.52241/0.49457 s, and roughly 222/284 MB native RSS; all 32 outputs matched the published hash. This single, mixed wall/CPU screen does not establish x86 or official performance. Raw samples are `arm-report.json`; `group-rss-arm.txt` and `maxgroups-rss-arm.txt` retain memory observations. No candidate has been promoted.

A second 15-pair ARM batch showed candidate/baseline median wall 0.07820/0.07542 s (3.7% slower), CPU 0.50190/0.45850 s (9.5% higher), with similar ~222/284 MB native RSS; all 32 outputs matched. The wall direction reversed from the first batch and CPU was higher in both. See `arm-repeat.json`. These observations do not support a reliable speed win and make the older x86 regression a material reason to defer target testing. Twenty additional forced long-name/selected-fallback comparisons also passed.
