# Scan-time anchored Boolean clauses (experimental; unselected)

`baseline.rs` is the exact selected source, SHA-256 `7d371fe84ce9f0fd9d3c7e6fdf02b6b37e0f1440319c654161b990cf27bb8bf3`. `candidate.rs` is a new isolated experiment and must not be selected until its exact-source tests and target measurements pass. It retains the complete Boolean CSR postings, existing bitmap evaluation and bounded per-chunk phrase summaries.

For each left-associative BOOL expression, the planner represents the current set as a union of conjunction clauses. The first term creates a positive clause. `AND t` adds positive `t` to every existing clause; `NOT t` adds negative `t` to every existing clause; `OR t` appends a new positive singleton. These transformations distribute intersection and difference over union and yield at most six clauses under the query grammar. Every clause has a positive term. The planner chooses its least frequent positive term in the existing input-derived sample as an anchor; sampling selects an execution strategy and cannot change membership.

For selected sparse estimated queries, each corpus worker stamps distinct Boolean terms in each complete document, then visits clauses anchored by terms that document contains. Positive stamps must be present and negative stamps absent. A bounded per-query chunk summary counts each matching document once even when multiple clauses match. Chunks retain their original order, so counts, exact ID sums, and the first ten IDs merge in order. Full original postings remain available for every Boolean term. Dense/OR-heavy estimates use the original bitmap evaluator directly.

At most 20,000 queries are selected and at most 12 workers are created. Each selected query has a per-chunk budget of 64 clause evaluations. When a query exceeds the budget in any chunk, that chunk lazily removes its clause entries from local anchor lists. The global answer path then ignores *all* its partial chunk summaries and uses the original bitmap evaluator on complete postings. This caps repeated adversarial anchor fanout per query/chunk while preserving exact output, at the cost of extra worker-local anchor metadata and summaries. The cap is on the added scan plan, not a formal total process or cgroup memory bound. Different sample distributions can change performance and fallback frequency but not the computed answer.

`verify.py` builds temporary overflow/debug-checked versions. It forces the full clause path for the existing 5,364-expression × 64-membership algebra oracle and 40 mixed reference corpora. Its separate 10,005-query fanout fixture places sample-unseen terms after the sample, creates duplicate clauses/queries and a nonempty completed chunk alongside an aborted chunk, and validates every output and the actual diagnostic path. Forced budgets 0, 1 and 3 exercise early fallback. Temporary instrumented builds, test data and binaries stay outside the repository.

**Status:** neither candidate is selected. `candidate.rs` SHA-256 is `0be729058c44071c992661d7d36ab000189a02c8d2b63f45c06161c80219761f`; `flat.rs` SHA-256 is `2d1aa3d2c550250cdce34e47ace4bb509c263f97a20d2ff0d198a6c796ab0e1f`. The latter replaces worker-local `Vec<Vec<u32>>` clones with intrusive flat head/next arrays and lazy deletion, retaining the same fallback policy. Reverse list order may change which budgeted queries abort, never their exact output when correctly implemented.

On native shared macOS ARM, nine randomized full-seed pairs plus warmups produced baseline/candidate medians of **0.235323/0.292308 s wall**, **1.522092/1.893349 s CPU**, and **521,273,344/539,656,192 bytes process RSS**. All 20 outputs matched the official hash. A separate nine-pair run of the flat variant produced baseline/flat medians **0.354983/0.405709 s wall**, **1.789698/2.004589 s CPU**, and **481,230,848/489,373,696 bytes process RSS**, again all 20 hashes correct. The shared host's baseline changed materially between batches, so do not compare variants across runs; both paired comparisons are slower. Native process RSS is not cgroup peak. Raw observations are `arm-screen.json` and `flat-arm-screen.json`.

A one-run instrumented full-seed diagnosis selected the 20,000-query cap, generated 29,452 clauses, and found 3,708 selected queries aborted in at least one chunk; the partial summaries recorded 1,490,922 chunk-local hits. Instrumentation changes timings and is not a performance score. The allocation-heavy worker-local anchor-list clones motivated the flat-list variant, which still lost to baseline in its paired screen. Per-query budget and query cap bound the extra scan work, but do not imply a universal cgroup memory bound.

`python3 experiments/b-scan-clause-anchor/verify.py` passed on the exact `candidate.rs`: 5,364 expressions × 64 membership assignments, 40 mixed-reference corpora, and a 10,005-query high-fanout fixture. The latter instrumented 6,003 queries aborted with mixed chunk statuses; 2,001 had a non-aborted, nonempty partial summary, and all results matched exact expected output. Forced budgets 0, 1 and 3 passed. This checks the global fallback after partial aggregation, duplicate clauses and queries, and output order. The flat variant has only the full-seed hash screen, not this exhaustive/reference/forced-abort suite; `B_SCAN_SOURCE=flat.rs python3 experiments/b-scan-clause-anchor/verify.py` targets it if future investigation is justified.

Real Linux x86 AVX2 execution, independent source review, broader adversarial memory bounds and official cgroup measurement remain outstanding. No dataset or credentials are included. No Mac Docker was used.
