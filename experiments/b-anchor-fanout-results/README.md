# B phrase-anchor fanout on the public full seed

One native macOS ARM diagnostic run scanned the independently generated full seed-1 dataset at `/tmp/speed-b-full`. It compiled the existing `../b-anchor-fanout-profile/profile.rs` (SHA-256 `3226c21ee8e0a242ee66f5f0976afd82c65a343d291be8f03ad2fcc1c8d9b9ea`) using `rustc 1.95.0 --edition=2021 -O -C lto=fat -C codegen-units=1 -C panic=abort`, then ran the resulting binary with `SD_DATA=/tmp/speed-b-full` and `SD_OUT` set to a temporary output directory. It was instrumented, so no timing is claimed. The selected baseline source at the time was SHA-256 `7d371fe84ce9f0fd9d3c7e6fdf02b6b37e0f1440319c654161b990cf27bb8bf3`. The diagnostic output `results.txt` matched the published full-seed SHA-256 `f86973c210228141bcb6f1f1b10188ad2a9b65f71e7cd7cf4590b38de4e80927`.

The existing `../b-anchor-fanout-profile/summarize.py` aggregated eight independently reported document chunks (250,000 documents). It counted 1,397,134 occurrences of phrase-anchor tokens and 1,667,000 visits to phrase windows. Grouping candidates by `(phrase length, anchor position)` would still require 1,606,499 group probes, only 60,501 fewer than the visits (~3.6%). Of 17,601 anchor terms with nonempty lists, 16,579 have fanout 1; those account for 1,212,072 observed anchor occurrences. The histogram is in `report.json`.

This grouping count is a proxy, not the runtime of a trie: it ignores document-edge rejection, lookup costs, actual matches and vectorization. It counts list visits rather than individual token comparisons. The measured public seed and native ARM scalar-tokenizer path may differ from hidden seeds and x86. It does not show that all phrase-matching optimizations are unhelpful, but does not support a large win from merely grouping the current anchor lists on this input. The full dataset, binary and temporary output were not stored in the repository. No Mac Docker was used.
