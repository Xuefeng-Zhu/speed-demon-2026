# Cooperative pipeline — exploratory design only

One possible larger change is to overlap record parsing with distinct-name reduction. Each of `n` workers would retain one exact owner dictionary and drain a bounded inbox while parsing its input interval. It would batch events for each destination owner, directly reduce self-owned events, and use nonblocking sends. On a full destination inbox it would retain the batch and drain its own inbox before retrying, avoiding cycles of workers blocked solely on sending. Equal names would still route to the same owner. Original CRLF synchronization and the large-file fallback would remain.

Termination needs particular care: only after its final successful sends would each producer release-decrement an unfinished count; an owner would acquire-read zero, then confirm its inbox is empty before exiting. An abort flag and unwind-safe guard would be needed so a panic or disconnected receiver cannot leave peers retrying indefinitely. All workers must join before output. Very long records can delay the next drain, so progress is conditional on finite records and fair scheduling; there is no strict latency bound.

With batch capacity `E`, `B` inbox batches and 16-byte events, a rough transient payload bound is `16 * E * (n*n + n*B + n)` bytes plus channel/vector overhead. Owner dictionaries and worker stacks remain additional data-dependent memory. This idea adds channel synchronization and may increase CPU time; it has not been implemented, validated, measured, or compared with the selected owner approach, and the existing same-hash owner-skew issue remains.
