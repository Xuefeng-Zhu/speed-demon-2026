# Rust Track A percentile threshold

The selected implementation sorts latency groups with at most 16 entries and otherwise uses three successive selections. We tested changing the threshold to 8, 32, 64, 128 or 10,000,000; each test was generated by changing only the `if n <= 16` constant in `track-a/src/main.rs`. On macOS a temporary copy also changed the anonymous mmap flag from Linux 0x20 to Darwin 0x1000. Source files in the submission were not altered.

The exploratory six-run rotation on the shared ARM Mac returned medians 0.05777 s at 16, 0.05368 s at 128 and 0.04803 s at 10,000,000. However, a follow-up 15-run randomized-order comparison returned 0.06164 s at 16, 0.05850 s at 128 and 0.06240 s at 10,000,000. Every run matched the published full seed-1 output hash. See `exploratory.json` and `paired.json` for all measurements. Host contention was present; neither timing series is an official score or a reliable x86 prediction. In the follow-up, median process RSS was about 285 MB and includes the mapped input, not the official cgroup peak.

No threshold is promoted: the 128 result is small and noisy, and unrestricted sorting also has worse asymptotic behavior for large legal groups. A follow-up should interleave exact selected and threshold-128 Linux builds on the target CPU, verify random/reference cases including large one-group inputs, and compare prewarmed cgroup peaks and source counts.

`threshold-128.patch` contains the single Linux-source change. Apply it to a temporary source copy, build both versions with identical flags, and run `python3 experiments/a-rust-percentiles/compare.py --baseline /path/to/baseline --candidate /path/to/candidate --data /path/to/full-a-data --report /tmp/a-percentiles.json`. The portable driver was smoke-tested on both ARM builds; it verifies every output hash. Like the worker-count driver, it records process RSS, not cgroup peak.
