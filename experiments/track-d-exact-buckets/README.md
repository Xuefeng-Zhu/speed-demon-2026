# Two-pass exact-capacity D loader (unselected)

This experiment is based on the unselected capped-hybrid search, **not** the current selected packed u64 search. `baseline.rs` is the exact capped-hybrid candidate SHA-256 `671c639be3400209e83e080dfb54947affd30ca71dc34ec17804d24d70292d9c`; `candidate.rs` is `e4caa9848aadb4af327ef99cd00a2e8a0454c6ce28ea226c2485a84d44330e0e`; and `packed.rs` is the selected packed baseline `793d13729fe4dabe2a1ed272fef78e19567456676ed8df52c075bc4ac33ebd05`. No selected source changed.

Within each parser's existing byte slice, a first pass counts forward and reverse edges for each destination bucket. Each `Vec` is then created with the corresponding count, and the same immutable bytes are parsed again to scatter the same edge tuples using the same mapping. Thus, for valid inputs, the sum of *requested* edge-bucket capacities is exactly `2*m` tuples: 120,000,000 bytes for five million edges if the target lays out `(u32,u32,u32)` in 12 bytes, instead of relying on geometric growth. This does not guarantee actual allocator footprint, freed-page behavior or an 8 GiB parent-cgroup bound. It also does not address other loader buffers, search state, stacks, kernel charges, or page cache. The original hybrid's other assumptions and caveats apply unchanged.

Independent instrumented tests in `../track-d-exact-buckets-independent/` checked 480 small, empty, random and all-skew graph/worker configurations, asserted space before every scatter, and compared both CSR edge multisets with input. A debug/overflow-checked build also passed 16,000 random Dijkstra comparisons, 36,864 exhaustive queries, cutoff boundaries, packed-node and max-weight boundaries, a maximum-size maximum-weight chain, and 6,000 repeated/unreachable queries. `verify-fallback.py` rebuilt with forced queue capacities 0, 1 and 2; each passed 16,000 random Dijkstra comparisons and cutoff boundary checks. These checks were on macOS ARM; x86, official cgroup and all hidden seeds remain unverified.

Test artifacts: independent `run.py` SHA-256 `3244ecc380c73259eb5a1e7a194ad721f8c5715bec1134b71ba5d0f28b5e2014`, independent `loader-tail.rs` `6a340dd9e789352fceeef6f9db220645c3a437e844a7b42d19165a7a02f3f08f`, `compare.py` `95f672d637097c25fae5c9e62f1e8b6dcb3cf945cbb06791f21d38810ca26937`, and `verify-fallback.py` `aff7be39446870d094076481291a2ecd98335511cd9a38009949ba416e6d45ae`.

Two randomized three-way 15-pair native ARM **sample** batches used the official seed-1 sample, verifying 48 hashes per batch. The first (`sample-arm.json`, SHA-256 `b96a05fda1149d4fc7b48b2399f0e71b5790c1c5e7d26cbf5606eb08a4043467`) may overlap an independent 0.27-second smoke test around 11:15:43 UTC; do not use it as decision-grade performance evidence. The later isolated repeat (`sample-arm-repeat.json`, SHA-256 `3ad1a092bee10be70cf04d34e1ba2e1e7a7d671d93475077dc247d0faf5c73ea`) had median wall candidate/hybrid/packed `0.021710/0.019960/0.020624` seconds, CPU `0.115167/0.103194/0.102424` seconds and maximum process RSS `45,711,360/44,433,408/55,492,608` bytes. The loader candidate was about **8.8% slower** than hybrid in this short sample; these are shared native ARM measurements, not full-data, x86, official scoring or cgroup results.

No Docker was run on the Mac. This candidate is retained for analysis, not selected or submitted. A stronger application-level bound would also require controlled allocator behavior, fixed stacks, and a bound on the complete parent-cgroup accounting; synthetic peak tests alone would be evidence, not an all-holdout proof.
