# CRC32C endpoint hash (experimental, not selected)

`baseline.rs` is the selected Track A source at e88ee2c (SHA-256 `9aa7eb44c30fbfc5b701ff9467d26b0a27e765520c5e766ef90d0ea6b04d85fc`). `candidate.rs` uses x86-64 SSE4.2 CRC32C for endpoint words, placing the 32-bit CRC in the high half of the existing u64 hash so the table's high-bit bucket selection works. Its non-SSE4.2 build uses the original multiply hash; full endpoint byte/length equality and dynamic table growth remain. The exact candidate source SHA-256 is recorded by `shasum -a 256 candidate.rs`. The actual Linux x86 intrinsic path has **not** been executed or benchmarked; a standalone helper typechecked only as Windows x86 metadata with x86-64-v3.

A test-only Darwin build substituted a bitwise software CRC32C recurrence for the intrinsic and changed the anonymous mmap flag from 0x20 to 0x1000. It matched the full seed-1 hash, the independent 0/1k/100k/100k oracle suite, 14 page-end reference fixtures, and a 5,143-endpoint forced-zero-hash/growth reference suite over workers 1/2/3/7/12/32. With `-C overflow-checks=yes`, the unchanged baseline SWAR latency parser panics on a legitimate test latency because its arithmetic is intended to wrap in official release; the forced-collision suite above used official-style release overflow behavior. This debug observation is not evidence of a release output defect.

`collision-family.py` uses linear algebra over GF(2) to generate distinct grammar-valid endpoints with the same CRC, verifies their hashes, and compares all output bytes against the official reference. On a shared ARM Mac with one line per endpoint, software-CRC simulation versus original hash had one-worker wall 0.0128 vs 0.0032 s at 1,842 names and 0.0984 vs 0.0054 s at 5,143 names; output matched at workers 1/2/7/12. These deliberately constructed corpora are not the published generator distribution and the simulation does not measure hardware CRC speed. Nevertheless, repeated traffic concentrated on such keys can amplify linear-probing costs. A CRC-only change has **not** been selected; a collision-bounded fallback or independently mixed hash and real x86 validation are needed before consideration.

Reproduce the algebraic family with `python3 experiments/a-crc32c/collision-family.py --count 1842 --binary /path/to/a --reference official/reference/a_ingest.py`; use `--count 5143` to test growth. Test a release-compiled x86 candidate and baseline against references and guard/page edges before any timing. All input is generated at runtime; no cached answers or credentials are included. No Mac Docker was used.
