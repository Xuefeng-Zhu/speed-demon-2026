# C dynamic input scheduling — unselected experiment

Baseline is exact selected salted-owner SHA-256 `0aa4cbccf08b05a59aadbe7eaf23a931e468a95f76463a95100a142e8221bc08`. The candidate splits the input into four times as many byte-proportional chunks, aligns each internal boundary to the next CRLF, and distributes chunks via one atomic counter to the original number of parser workers. Each worker retains one aggregation and one set of owner bins. Existing reducer routing, exact comparisons and fallback remain unchanged. The queue adds one atomic counter; bin/event buffers are still allocated per worker rather than per chunk, so event storage retains the baseline O(records) bound. Boundaries are nondecreasing: duplicate cuts result in empty chunks; adjacent chunks share endpoints and cover the same records exactly once. This is an experiment, not selected.

The candidate matched 24 reference corpora at five worker counts and 357 hostile reference comparisons at workers 1/2/3/7/12/32/64. The latter included quoted bare LFs, BOMs, a 120,000-byte name, a region spanning several desired cuts, and 236 duplicate-cut incidences. The source was changed only before these checks; `cut_oracle.py` records targeted coverage. Independent static review and actual Linux/x86 tests remain outstanding.

Nine randomized native ARM pairs plus warmup measured candidate/baseline median wall 0.08629/0.09064 s and CPU 0.51159/0.50619; a 15-pair repeat measured 0.09019/0.09343 s and CPU 0.50807/0.51073. All 52 outputs matched the public full hash. Raw JSON retains samples. A modest wall difference with effectively tied CPU is not a target score or firm win; host load can vary. Every chunk independently recomputes both CRLF bounds, so pathological long records can cause repeated scanning proportional to the number of cuts; this issue requires fixing or measurement before target consideration. No Mac Docker was run.
