# Narrow pool occupancy bitmap (unselected)

The exact batch16 baseline is SHA-256 `7fd333be25133a78264cb4b84441de46d4c8bcbfd73914af23761f23d8c47f17`; candidate `343d15472ae055432dce4d4c4bbddb4b6483c061e66f613bd35ee6defeea1ca0` keeps a 64-bit occupied-bucket mask for `FastHeap` to avoid scanning `head` for the first nonempty bucket. Since `Search32::reach` inserts only distances below `u32::MAX`, and radix `last` is a prior narrow inserted key, all live heap bucket indices are at most 32. The mask is updated on insert, redistribution, final bucket-zero pop, and clear. The wide indexed fallback remains unchanged. This invariant depends on the narrow-only use of `FastHeap`; its standalone push is not valid for arbitrary u64 keys above the stated range. No independent code review, x86, cgroup, or hidden-data tests have been done.

`python3 experiments/track-d-pool-bitmap18/verify.py` passed debug/overflow builds at capacities 0, 1, 2, and 65,536 against 16,000 random directed graph queries and 36,864 exhaustive 3-node answers per build, cutoff and node boundaries, maximal-weight chain and repeated/unreachable cases. `run-pool-property.py` passed a 1M-operation monotone multiset model while auditing every one of the 33 mask bits against actual bucket heads. These finite tests do not prove all-input correctness or the full 8 GiB cgroup bound.

A serialized 11-pair full-seed native shared-Mac ARM screen (one warmup per candidate, randomized order) used separately generated public seed-1 inputs with both published input hashes verified. All 24 executions produced the official full output hash. Median wall: bitmap **0.250257 s**, baseline **0.245489 s** (bitmap ~1.9% slower); median CPU 1.790450 versus 1.778847 s; maximum native RSS 585,383,936 B for both. Raw per-run evidence is `arm-full.json`. This modest negative result on a shared ARM host does not establish target x86 performance, but supplies no reason to prioritize promotion. No Docker was run on the Mac.
