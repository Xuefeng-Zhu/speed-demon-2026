# D CSR-mode specialization (unselected)

`baseline.rs` is exact selected batch16, SHA-256 `7fd333be25133a78264cb4b84441de46d4c8bcbfd73914af23761f23d8c47f17`; `candidate.rs` is `528e3e327172a0ce87e1ee854aed21710fb12fb401511594e63e80e2d431897d`. The only functional change passes a constant CSR mode to both narrow and wide searches, enabling two compiled versions of their edge iteration instead of checking compact-array emptiness on every edge. At query entry, nonempty compact arrays select packed mode; otherwise the u64 path is used. Both graph directions share n and m, thus agree on representation; when m=0 no adjacency is read and either choice is equivalent. Existing narrow queue capacity, failure cleanup, u32 cutoff, and exact wide fallback remain. Monomorphization may increase executable size. The hidden-input 8 GiB parent-cgroup peak is not proven.

Independent static review found no concrete mode selection, fallback, empty-graph or `2^21` boundary defect under the baseline's valid-input assumptions. `python3 experiments/track-d-csr-specialize21/verify.py` compiled overflow/debug-checked pools with caps 0, 1, 2, 15, 16, 17 and 65,536; each passed 16,000 randomized Dijkstra answers and 36,864 exhaustive directed graph answers, and individual cutoff boundary checks. Caps 0, 1 and 65,536 separately passed node boundaries `2^21` and `2^21+1` with zero/short/wide weights and wide fallback; the latter two additionally passed the maximum-size max-weight chain and 6,000 repeated/unreachable queries. `empty.py` passed zero-edge cases for 1, 2, `2^21`, and `2^21+1` nodes. These finite macOS ARM tests do not prove all inputs or Linux/x86 behavior.

On independently generated public full seed-1 data, all 88 warmup and timed executions produced the official SHA-256. The first 11-pair shared ARM screen was **partly contaminated** by an overlapping correctness process and is recorded in `arm-report.json`; its medians were 0.242165 s candidate vs 0.247954 s baseline. Two subsequent 15-pair screens were serialized: `arm-repeat.json` candidate/baseline median wall **0.243649/0.246500 s** (1.2% lower), CPU **1.752158/1.768859 s**; `arm-third.json` **0.254931/0.264195 s** (3.5% lower), CPU **1.745616/1.779546 s**. Native maximum process RSS varied by scheduling and is not parent-cgroup peak. These marginal ARM results do not establish target x86 or official scoring performance. No Docker was run on the Mac.

Reproduce in a free native window with `python3 experiments/track-d-csr-specialize21/compare.py --data /path/to/full-d --build-dir /tmp/d-csr-mode --report /tmp/d-csr-mode.json --runs 15 --seed 583161`; the script compiles both sources with identical optimized flags and checks each full output hash. Run `python3 experiments/track-d-csr-specialize21/verify.py` and `python3 experiments/track-d-csr-specialize21/empty.py /path/to/candidate` for correctness. Target x86, cgroup memory, official board score and a complete hidden-data proof remain outstanding. No selected source was changed.
