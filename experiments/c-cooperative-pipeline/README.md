# Cooperative owner pipeline experiment — unselected

Candidate SHA-256 `5c301280b8a1d587a8ae407aebaddb9e5aa08cf94864ebdb5076719c916b1b09`; baseline `6e12627e96f0a0433e567413ccacc1a5d7fdf2de8f4781a3f826c260499783dd`. Replaces the compact path's separate parse and owner-reduction phases with per-worker owner dictionaries, direct self-reduction, and nonblocking 256-event batches over capacity-two inboxes. On full outbound queues workers drain their own inbox. Each worker remains alive and drains until all producers have completed all sends; it checks the inbox again **after** observing zero. The distinct-name dictionary, owner hashing, group bits, record synchronization and large-file fallback are otherwise preserved. An unwind guard sets a shared abort flag; queue loops check it. A separate parent-side guard sets the same flag if scope setup or a partial thread spawn unwinds. No selected source is modified.

An independent review found and prompted a fix for a termination race: a final send could arrive after an initial Empty and before zero was observed. The post-zero read fixes it. `termination-race.py` forces the interleaving on exact source; the fixed version matches the reference and an automatically reconstructed old version deterministically loses the final batch. Subsequent static review found no further defect in termination ordering, but correctness testing cannot guarantee liveness on every scheduler. Progress assumes finite records and fair scheduling: one very long field can delay draining. Equal-full-hash names still concentrate at one owner. Abort tests exercise panic propagation, including parent unwind after partial spawn; an aborting process crash is not recovered.

Tests against revised exact source (native ARM, no Docker):

- 24 hostile corpora × 5 workers versus official reference; parser properties and actual protected-page guard tests.
- 20 long-name/collision/fallback cases, including nine actual sentinel reparses; 20 lookup-group cases; 12 owner/full-hash collision checks; 357 CRLF/cut comparisons at 1–64 workers; owner mapping and gate properties.
- `stress.py`: capacity-one queue with one-event batches, observed full queues, 1/2/7/32/64 workers and output equality; injected parse and full-queue panics at 7/32 workers terminated within 60 seconds with no output.
- `cyclic.py`: every one-slot inbox is prefilled and all 2/7/32/64 workers are held at Full before any may drain; after release each queue delivers both groups and terminates within 60 seconds.
- `partial.py`: observed a non-full final outbound batch and matched the official reference.
- `partial-spawn.py`: forced parent unwind after a worker entered; process terminated without output within 30 seconds.

Transient event payload approximately `16 * batch * (n² + n * inbox_capacity + n)` bytes, plus channels, allocation overhead, input mappings, dictionaries/bitsets, aggregation and stacks. For n=16 and batch=256, inbox capacity=2, this is about 1.2 MiB. This does not bound total memory: dictionaries and group bitsets depend on input. Potential extra queue allocation, locks, CPU, scheduler overhead and hot-owner skew require measurement. A 15-pair randomized native ARM screen against exact fused baseline measured median wall 0.11383 vs 0.07584 s (50.1% slower), CPU 0.8208 vs 0.4496 s (82.5% higher), and process RSS 210.25 vs 270.27 MiB (22.2% lower). All 32 full seed outputs including warmups matched; raw data are in `arm-15.json`. This is a non-official shared-host screen, not an x86 score; actual AVX2 fallback and target cgroup behavior remain untested. The substantial wall/CPU regression makes promotion unattractive under speed-first priorities.
