# D radix redistribution without count churn (not selected)

`baseline.rs` is exact selected Track D. `meeting.rs` retains the same radix heap bucket ordering but redistributes entries directly into destination buckets, rather than subtracting their count and calling `push` (which restores the same count one entry at a time). The monotone radix invariant puts every redistributed entry below the source bucket; all pending entries, node IDs and keys remain unchanged. There is no input or answer caching.

Both builds passed the published full seed-1 hash in all 36 warmup/measured executions across two randomized native shared-Mac ARM comparisons. The first 7-pair batch was severely contended: median wall 0.45544 s candidate versus 0.47672 s baseline, CPU 1.95923 versus 1.89138 s. A 9-pair repeat was effectively tied: 0.26974 versus 0.27073 s, CPU 1.84080 versus 1.83335 s, maximum native RSS 535,658,496 versus 534,675,456 bytes. Individual runs and source hashes are in `report.json` and `repeat.json`. This is not x86, official scoring, or cgroup memory; the result does not justify promotion.

Both implementations passed 80 random directed-graph Dijkstra fixtures (16,000 queries each), 4,096 exhaustive three-node directed graphs (36,864 Floyd–Warshall queries each), a full-size maximum-weight chain with unreachable and self cases, and 6,000 repeated/unreachable queries, using `experiments/track-d-balanced-frontier/{oracle,exhaustive,extremes}.py`. Run `python3 compare.py --data /path/to/generated-full-d --build-dir /tmp/d-redist-build --report /tmp/d-redist.json --runs 9` for a native paired recheck. No datasets, cached answers or credentials are included. No Docker was used.
