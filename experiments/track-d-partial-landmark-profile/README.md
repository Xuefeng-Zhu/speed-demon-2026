# Partial-landmark reuse diagnostic (not a candidate)

`profile.rs` instruments the exact selected positioned-read baseline in `baseline.rs`. It does not change its answers or search schedule. After each search, it treats the forward heap's last monotone key as a radius R and conceptually caps source distances at R; exact distances strictly below that radius are already settled. For a potential later query (a,b), the directed triangle inequality yields the admissible lower bound `max(0, min(d(L,b),R)-d(L,a))` whenever d(L,a) is below R. Landmarks with the same source as the target query are excluded, including duplicates. All distances and answers are runtime data; this is only an offline analysis, not a solution using saved answers.

One instrumented shared ARM full seed-1 run produced the published output SHA-256 `a23dbdf0a3e49cc8901310a9ee1dc6a9a569a85297b6da75c2a7002cb2ed277e`. Across 1,994 nontrivial search landmarks it observed 4,365 landmark/query pairs with query source in the landmark radius. If every completed search were available in advance, an upper bound was positive for 1,210 queries, reached 25% of their true answer for 725, 50% for 345, and 75% for 172. Given the true answers and every landmark beforehand, an optimistic greedy selection of 1/2/4/8/16/32 landmarks covered 11/20/37/66/108/165 queries with a bound at least half their distance. This deliberately optimistic selection ignores lookup, storage, scheduling, consistency implementation, A* CPU costs, memory and the impossibility of accessing future searches; it is not an implementation or benchmark. It suggests a handful of reused landmarks are unlikely to provide the desired broad substantial speedup. Full formal correctness and x86 performance have not been evaluated. No Mac Docker was used.
