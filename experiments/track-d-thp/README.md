# Track D transparent hugepage advice (experimental, not selected)

`baseline.rs` is the selected D source. `meeting.rs` requests `MADV_HUGEPAGE` for full 4 KiB Linux x86-64 pages entirely inside each worker's freshly allocated, zeroed `dist` vector. It ignores advice errors and uses the existing algorithm unchanged. This is an operating-system hint, not `MAP_HUGETLB`, explicit hugepage reservation, or data-dependent answer selection. The hypothesis is lower TLB pressure during many random shortest-path distance lookups. Hugepage policy, fragmented backing and cgroup accounting can nullify the hint or increase page fault time and memory; x86 and actual scoring environment measurements are required.

The Linux conditional branch has been typechecked in a Rust metadata build with Linux cfg enabled. An overflow-checked native Mac build, where the Linux hint is excluded, passed 80 random graphs / 16,000 independent Dijkstra queries, 4,096 exhaustive three-node directed graphs / 36,864 queries, a full-size maximum-weight chain and 6,000 repeated/unreachable queries. This does **not** execute or verify the Linux syscall path. No selected source changed and no Docker was run.

Before considering selection, compile and execute both exact sources on the native target kernel, verify all output hashes, randomized graph oracles, exhaustion and maximum-weight chain, and monitor cgroup peak and memory/page-fault tradeoffs. Confirm through an isolated diagnostic (for instance, page mapping information from a fresh standalone instance) whether the advice is accepted and transparent hugepage policy actually changes backing; do not treat a ignored hint as evidence of a positive or negative THP effect. Time uninstrumented binaries with `compare.py` on warmed full seed-1 data, in randomized pairs without competing tests. A sanitizer or independent review of the FFI and in-allocation range is required. Never use explicit hugepage reservation or sysctl modifications.

Independent source review found no alignment, live-allocation bounds, ownership, thread safety or FFI-signature defect under the official x86-64 4 KiB base-page environment. Linux `MADV_HUGEPAGE` is advice value 14; the result is ignored. The advice can persist after the allocation is freed if the allocator reuses the mapping; the range statement covers the allocation while it is live, not future allocator reuse. The final source SHA-256 is `f950514fc718d915f2392af72394ab2cdad8f44023a54396cdc32eff84120f4d`. It still needs exact-path execution on Linux, including forced workers, target paired benchmarks, actual advice/THP diagnostics and official sandbox/cgroup verification before any selection.

## Dot VM x86 result

The parent-run shared native x86 VM paired comparison found 34–39% lower wall time and 36–40% lower CPU time, with median native RSS unchanged. The Linux advice succeeded and an isolated diagnostic observed 24 MiB of transparent-hugepage backing versus zero in the baseline; no system policy was changed. Across this and four other packages, 272 full hashes, 40 alternate comparisons, AVX2/guard, collision and graph-oracle checks passed. These figures are native VM results, not official cgroup or scoring-box measurements. The hint was temporarily adopted for official validation; if THP is unavailable or denied, the call is ignored and the existing algorithm continues.

Official practice batches measured 0.457316 s and 0.400150 s with the hint, against a prior baseline batch at 0.374915 s; all gates passed. The no-hint source was restored on the speed-first criterion. See `track-d/PERF.md` and board snapshots for the limitations of separate runs.
