# Sparse 64-document word merges (unselected)

This experiment is based on the exact selected B source `baseline.rs`, SHA-256 `7d371fe84ce9f0fd9d3c7e6fdf02b6b37e0f1440319c654161b990cf27bb8bf3`. Candidate SHA-256 is `6dfbc0fcc208b9e55e496bdc3947c4c3c221483efcb67f23b688e37e1d4bc7ea`. It changes only Boolean query evaluation; tokenization, postings, phrase summaries and the 64 MiB dense-cache payload cap are unchanged.

If the sum of all operand document frequencies is at most 512, each operand's globally ordered postings are grouped into sorted `(64-document word index, u64 mask)` entries. The running result is merged with each grouped operand in the original left-to-right order using exact union, intersection or difference. The result's nonzero words are visited in ascending order to compute the exact count, ID sum and first ten IDs. Larger queries use the original dense bitmap path. Every sparse intermediate contains at most the sum of operand postings (at most 512) nonzero words; three scratch vectors are reused within each query block. Rust allocation capacity can exceed element count, so this bound is not by itself a full process or cgroup bound. Repeated operands are included in the threshold sum, which can conservatively send a query to the original path but cannot change its answer.

`verify.py` compiles temporary optimized overflow/debug-checked forced-sparse, normal, and forced-dense versions. It passed 5,379 reference queries on 511/512/513-posting boundary cases, 5,364 expressions × 64 membership assignments under forced sparse, and 40 mixed-reference corpora each for normal and forced-sparse. `boundary.py` traced the actual 511, 512 and 513 path decisions and matched an independent oracle on 250,000 documents crossing 64-bit word, worker-chunk and high-ID boundaries, including repeated and missing operands, `AND`, `OR`, `NOT`, mixed left-associative expressions, dense fallback and top-ten order. These are finite tests, not complete proof of all inputs or an x86 SIMD guard test.

Two serialized 15-pair native macOS ARM full-seed screens plus one warmup per binary used the pre-existing `/tmp/speed-b-full` dataset read-only and verified all 64 outputs against the published full hash `f86973c210228141bcb6f1f1b10188ad2a9b65f71e7cd7cf4590b38de4e80927`. First batch median baseline/candidate wall was 0.261914/0.267360 s and CPU 1.533094/1.528662 s; the second was 0.238412/0.237218 s and CPU 1.534929/1.506231 s. Median native process RSS was about 519/517 MB. The small, inconsistent wall change does not support a substantial improvement; the experiment remains **unselected**. Raw observations and randomized pair order are in `arm-a.json` and `arm-b.json`. ARM scalar tokenization, process RSS, and a shared host are not x86 AVX2, official scoring or cgroup evidence. No Docker ran on the Mac.

For reproduction, compile `baseline.rs` and `candidate.rs` with identical release flags, then run `compare.py --baseline <binary> --candidate <binary> --data <full-data-dir> --expected f86973c210228141bcb6f1f1b10188ad2a9b65f71e7cd7cf4590b38de4e80927 --runs 15 --report <file>`. Run `python3 experiments/b-word-sparse-merge/verify.py` and `python3 experiments/b-word-sparse-merge/boundary.py` from the repository root. Generated tests and outputs use temporary directories; no dataset is included.
