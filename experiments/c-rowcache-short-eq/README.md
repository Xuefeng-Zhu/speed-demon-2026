# Exact short-name equality on row-cache hits (unselected)

`baseline.rs` is the earlier owner-cache C source (SHA-256 `76b341e2b7e880fe4ceeee220206a63b48cd247bba4448aa7991a7ad825e8dd2`). The candidate only changes the owner row-cache hit check. It compares length first and, for equal lengths 8 through 16, compares the first and last eight bytes with guarded unaligned reads; their union covers every byte. All other lengths use the original exact slice equality. Full hash checking, map misses, exact collision fallback, input parsing and owner routing are unchanged. Reads are in-bounds because each slice has at least eight bytes; no alignment is assumed. Different pointers, embedded NULs, escapes and trailing spaces remain byte-exact.

This is an isolated experiment, not selected or officially tested. Candidate SHA-256 `8ab8977bb9956a686792769eb6cd758726538b8dcac4f4336b74539fba23104c`. Independent static review and 8,650,752 exhaustive replacement cases plus 500,000 randomized overlapping-slice cases passed; see `../c-short-eq-independent/README.md`. Actual Linux x86 guard and timing checks, complete files over 4 GiB, and cgroup measurement remain outstanding.

On macOS ARM, the exact candidate passed lengths 0–256 over 32 alignments with a single differing byte at every position, protected-page placement at either end of a readable page, and 150,000 forced-hash group-model operations with repeated cache hits. It also passed 24 mixed reference corpora × five worker counts and eight forced-hash corpora × five worker counts. The same source has not been run through the x86 path or under a sanitizer.

Two serialized randomized 15-pair full seed-1 ARM batches, after one warmup pair each, produced the official output hash on all 64 runs. Baseline/candidate median wall times were 0.072965/0.070446 s and 0.073012/0.070522 s; CPU medians were 0.424129/0.413236 s and 0.431362/0.404279 s. Median process RSS was essentially unchanged (about 287 MB). These results suggest a modest ~3.4% native ARM wall improvement, not a scoring-box or x86 claim. Individual results are in `arm-report.json` and `arm-repeat.json`. The generated input was removed after the tests; no Docker was used.

`python3 experiments/c-rowcache-short-eq/verify.py` runs exhaustive length/alignment/differing-byte checks, protected-page tests, a forced-collision group model, and 24 normal plus 8 forced-hash mixed corpora across five worker counts. Use `--avx2` only on a capable x86 Linux host. The official reference is at `official/reference/c_join.py`.

For serialized full-data benchmarking compile both sources identically, then use `compare.py --baseline /path/to/baseline --variant /path/to/candidate --data /path/to/generated-full-c --runs 15 --report /path/to/report.json`. No input data is included. Native ARM timings and process RSS are not target scoring or cgroup results; actual x86 paths and guards must be tested before promotion.

## Baseline and target

This experiment and its reported ARM results compare against `baseline.rs` SHA-256 `76b341e2b7e880fe4ceeee220206a63b48cd247bba4448aa7991a7ad825e8dd2`. The currently selected dynamic-partition implementation is a different source, SHA-256 `bcd4d7715bffd8a3dc062cad6e7aa0886a96d659fcc9170735c4d4d123f67eae`, included separately as `../c-rowcache-dynamicparts/parts4.rs`. This candidate has not been rebased onto or benchmarked against that current source. Do not replace the current selected source with `candidate.rs`; a combined variant requires deliberate rebase, renewed correctness checks, and a paired target comparison.

The ARM protected-page checks and reference runs do not establish actual Linux x86-64-v3 code execution, guarded-page behavior on that platform, x86 speed, official cgroup peak, or hidden-data correctness. `verify.py --avx2` exercises the x86-64-v3 build only on compatible x86 hardware; it must be run there along with the independent runner and the full paired benchmark before considering this candidate.
