# Independent review of bounded CRC endpoint lookup

Reviewed candidate SHA-256 `9028986cf2546dfc008cf05dfdb32648cf64b6536223b933fe820cd69deb89e9` against selected baseline `4af40353f517f566217b0f882ec25d8002f61d211dcc479c53f8a1dd5de7ed88`. Static review found no concrete difference in endpoint identity, per-hour records, or fallback output under the official input grammar and 64-bit target.

`parse_fast` owns its entire temporary `Chunk`. A bounded lookup failure propagates `None`, dropping that chunk, its tables and record vectors before `parse_original` reparses the same original half-open shard; neither parser writes output. Successful fast parsing records IDs in insertion order, then rebuilds a new table from that same ordered name list using the baseline hash. Exact endpoint bytes are checked after hash equality, so a hash collision does not merge distinct endpoints. Rehash while growing uses the same bounded operation; failure also discards the entire shard. The CRC instruction is compiled only when x86-64 and SSE4.2 are compile-time target features, while the ordinary fallback uses the unchanged baseline parser. Loads use the existing bounded `load` over the padded mapping; this change introduces no additional memory load before feature gating.

`python3 experiments/a-crc-independent15/run.py` pins the exact source, builds a temporary test copy with the portable `sd_crc_sim` path and release-style arithmetic, and runs two independent properties. They compare the canonical hash against a separate chunk-based oracle for 32 alignments and 1,025 lengths; insert and retrieve 3,000 distinct endpoints across a table growth and rebuild in exact ID order; and force a single-slot collision chain, confirming 49 distinct entries are accepted and the next distinct entry requests fallback. Both tests passed on native macOS ARM. A dead-code warning for the inherited `madvise` declaration was emitted.

These are finite tests. They do not execute the hardware CRC intrinsic or reproduce the Linux x86 mapped-page environment. Actual x86 SSE4.2 preflight, protected-page and full-output tests, adversarial restart/mixed-shard stress, official practice and paired target timing remain required. The baseline SWAR latency parser intentionally relies on release wrapping in some operations; checked-overflow builds are not the production arithmetic and require carefully documented test-only wrapping. No Mac Docker was used.
