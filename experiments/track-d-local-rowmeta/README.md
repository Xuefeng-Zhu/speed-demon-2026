# Per-worker distance and row metadata (unselected)

The baseline is exact positioned-read Track D source SHA-256 `ac9674a11b90244c63a518ee94eb7a9547353540ff564672aaa128ac4851a2ea`. The isolated candidate `meeting.rs` has SHA-256 `19c5eeff596e955e8fac51f5e40ff88cf7a57540023f72f45e051fefeb471d8b`. Each worker builds a 32-byte node record containing the existing paired 64-bit complemented search distances plus forward and reverse CSR start/end offsets. Expanding a node reads its CSR row from that record, potentially reducing random pointer-array loads. Cleanup resets only the two distances, retaining the read-only offsets. The candidate has not received independent code review and is not selected.

A debug-free ARM native shared-host seed-1 **sample** test ran one warmup and 15 randomized pairs using `compare.py`; all 32 output hashes matched the published sample output. Median wall times were candidate 0.030935 s and baseline 0.024345 s; median process CPU times were 0.133632 and 0.117498 s, and maximum native process RSS 81,068,032 and 59,047,936 bytes. Host activity and the short 20–30 ms execution times may affect results. This is neither full-size nor x86 nor official cgroup evidence, and the preliminary screen does not support promotion. Flags, source hashes and every observation are preserved in `sample-report.json`.

The optimized candidate passed 80 independent randomized directed graph fixtures with 16,000 Dijkstra-oracle queries, using `python3 experiments/track-d-balanced-frontier/oracle.py /path/to/meeting /path/to/meeting`. These checks do not establish correctness on every legal graph. No Mac Docker was used.
