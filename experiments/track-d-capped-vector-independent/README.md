# Independent vector-bucket heap review

This review concerns the isolated candidate `../track-d-capped-vector-buckets/candidate.rs`, SHA-256 `3496a3a8e06f35e5effeb162735eef44dbb0728a44d487be2a9a951e8763160a`. It does not select or modify competition code.

Static review found no concrete defect in radix redistribution, key packing, ties, stale entries or capacity fallback under the surrounding narrow-search invariant: inserted keys are strictly below `u32::MAX` and vertex IDs fit `u32`. Thus the packed `(key << 32) | vertex` is lossless and bucket indices are 0 through 32. Once a nonzero bucket's minimum becomes `last`, every entry redistributed from that bucket has a strictly lower bucket index; the loop cannot reinsert into the bucket it is draining. Moving entries does not change the global live count. Equal-key order is immaterial to Dijkstra; the existing stale-entry and exact wide-rerun paths are unchanged.

`python3 experiments/track-d-capped-vector-independent/run.py` verifies the candidate SHA and appends `test-tail.rs` to temporary copies compiled with optimization, overflow checks and debug assertions at pool capacities 0, 1, 2 and 65,536. Each build passed three tests. The default-capacity tests populate all 33 buckets with equal-key groups and the maximum supported key, check every pop against an independent `BTreeMap` multiset, fill all 65,536 live entries, assert the next insertion is refused, perform 20,000 model-checked pop/refill steps with continued refusal at capacity, then drain and clear/reuse. Tiny capacities also check empty, refusal and reuse behavior. These native ARM heap-model tests do not establish end-to-end graph correctness, concurrency, x86 performance or cgroup peak.

On a 64-bit target, 33 buckets each request 65,536 × 8 bytes: **17,301,504 bytes per direction**, compared with 1,048,576 bytes for the selected fast pool. At 12 workers and two directions this is **415,236,096 versus 25,165,824 requested bytes**, an increase of 390,070,272 bytes (about 372 MiB). Actual allocation, page residency, fallback state, loader, allocator and cgroup charges require separate evaluation; `Vec::with_capacity` provides no portable upper bound on allocation footprint. The candidate does not establish a formal 8 GiB peak. No Mac Docker was used.
