# Independent fixed-bucket review

Candidate SHA-256: `3496a3a8e06f35e5effeb162735eef44dbb0728a44d487be2a9a951e8763160a`. Baseline selected hybrid SHA-256: `671c639be3400209e83e080dfb54947affd30ca71dc34ec17804d24d70292d9c`. This is a static review, not a target-platform performance result or complete cgroup proof.

The candidate changes only the narrow heap. The caller inserts distances strictly below `u32::MAX`, so the packed `u64` preserves all key bits and the full `u32` vertex, and the XOR-based radix index is in 0 through 32. The chosen minimum becomes the new monotone `last`; every item redistributed from bucket `i` then belongs to a bucket lower than `i`. Redistribution changes no live-entry count. The existing caller performs its original touched-state cleanup and exact indexed-wide rerun if insertion fails. Each worker exclusively owns its two queues.

Each bucket requests capacity for `POOL_CAP` entries at construction. Before any new insertion, the heap rejects a push when its global count is already at that cap. A bucket's length is at most the total live count; during redistribution, popping before pushing preserves that bound. Thus on valid heap states no bucket needs logical growth. `Vec::with_capacity` guarantees at least the requested capacity, but does not give a portable upper bound on allocator footprint. Capacity zero returns the existing exact fallback before initial insertions.

At the official full size with 12 workers, the narrow bucket payload requests `12 * 2 * 33 * 65,536 * 8 = 415,236,096` bytes. The selected hybrid requests `12 * 2 * 65,536 * 16 = 25,165,824` bytes for its narrow pools. The difference is 390,070,272 bytes, excluding vector headers and allocator overhead. Adding that difference to the prior *conditional* 2,265,040,180-byte hybrid accounting produces 2,655,110,452 bytes, about 2.473 GiB, with 5.527 GiB nominal headroom below 8 GiB. This inherits the growth, allocation, cache and stack assumptions in `../track-d-indexed-memory-bound/README.md`; it is not a bound on parent-cgroup peak. There are 792 per-bucket allocations, whose allocator retention and kernel/page-table charges require target-specific evaluation. Pages touched by different buckets can remain resident across queries despite the global live-entry cap.

No concrete correctness defect was found in this review. The separate `run.py` model covers capacities 0, 1, 2 and 65,536, all 33 buckets, ties, maximum keys, repeated full rejection/refill and reuse. Neither that model nor the sample ARM timing establishes real x86 execution, official performance, or a worst-case 8 GiB result.
