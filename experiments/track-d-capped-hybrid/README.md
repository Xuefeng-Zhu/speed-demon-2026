# D capped fast radix with indexed exact fallback (unselected)

This prototype compares against the exact u32-cutoff `baseline.rs` SHA-256 `5c07ea85035e37157f77c66ccd06d86cefd022cc42311aa95497f78dc4a6d451` and selected packed u64 `packed.rs` SHA-256 `793d13729fe4dabe2a1ed272fef78e19567456676ed8df52c075bc4ac33ebd05`. Candidate `candidate.rs` SHA-256 `671c639be3400209e83e080dfb54947affd30ca71dc34ec17804d24d70292d9c` is isolated, unselected and unsubmitted.

Each narrow search direction has a contiguous fixed-capacity pool of 65,536 `PoolNode` entries plus 65 radix bucket heads. Nodes are recycled using a free list; no queue allocation or growth occurs after initialization. It retains duplicates and ignores stale pops as in the original. If a new entry cannot be allocated, the partially updated search and both heaps are cleaned and the query is rerun from scratch using the exact indexed u64 wide search. The same exact wide search is used when the original u32 cutoff rule requires it. A zero-capacity build immediately requests the exact fallback; a self-query returns zero. The wide indexed search has one entry per vertex per direction, fixed link arrays and decrease-key unlink; worker count is capped at 12. Both narrow and wide states may remain allocated after fallback.

An independent static review in `review-static.md` found no concrete defect in pool reuse/redistribution, reset after partial touches, cutoff fallback, indexed wide search or worker cap. `run-pool-property.py` passed one million randomized insert/pop/clear operations against a multiset model under debug and overflow checks. `run-forced.py` verified capacities 0, 1 and 2 repeatedly exercise exact fallback and clear partial state. Four debug/overflow builds (0/1/2/65,536) each passed 16,000 random Dijkstra-oracle answers, 36,864 exhaustive graph answers, and zero, cutoff−1, cutoff, cutoff+1 and unreachable cases. Default capacity passed n=2^21 and 2^21+1 node/weight bounds. Default and cap=1 both passed a full-size maximum-weight chain and 6,000 repeated/unreachable queries. Every one of 96 sample benchmark outputs matched the published sample hash. Those checks were on native macOS ARM, not x86 or official cgroup.

Two randomized three-way native ARM sample screens, 15 pairs each after warmup, produced median wall seconds hybrid/u32/packed `0.020715/0.019021/0.022674` and `0.024025/0.021427/0.023809`. Hybrid was 8.9% and 12.1% slower than u32; compared with packed it was 8.6% faster then 0.9% slower. Corresponding CPU medians were `0.102223/0.091978/0.100263` and `0.112406/0.094457/0.109234` seconds. Maximum native process RSS was `44,498,944/41,025,536/56,737,792` and `47,513,600/38,420,480/55,181,312` bytes. Runs are short and on a shared host; ARM sample time and process RSS are not full-size x86, official scoring-box or cgroup evidence. Raw observations and flags are in `sample-arm*.json`. The default pool did not exhaust in an instrumented public full seed-1 run, but did exhaust in a separate broad-frontier stress test; see the native x86 findings below.

Memory accounting for full n=1,740,512 and 12 workers with all workers retaining wide fallback: narrow distances 8n, narrow touched 4n, wide distances 16n, wide touched 4n and wide links 16n per worker total 48n×12; two narrow 65,536×16-byte pools per worker add 25,165,824 bytes. Total requested search payload is 1,027,700,736 bytes; each touched array cannot contain more than n vertices and queue node storage cannot grow. A conservative, explicitly conditional loader/cache/stack accounting in `../track-d-indexed-memory-bound/README.md` gives about 2.265 GB listed payload including all query states. It is **not a formal 8 GiB parent-cgroup proof**: Rust Vec capacity/allocator over-allocation and retention, runtime, page cache, kernel and harness charges lack normative bounds in the official specification. Do not represent the prototype as proven cgroup-safe.

For dot VM evaluation, first inspect the archive, verify hashes, and ensure x86-64-v3 support. `python3 experiments/track-d-capped-hybrid/verify.py --cpu x86-64-v3 --extremes` compiles the four capacities with debug/overflow assertions and runs independent oracle, forced exhaustion, thresholds, packed boundaries and max-weight/repeated tests. Generate full seed-1 data independently, then use the comparator twice with different `--seed` values and `--data` pointing to that dataset; it records wall, CPU, native process RSS, source hashes and checks every output against the official full hash. For example:

```
python3 experiments/track-d-capped-hybrid/compare.py --data /path/to/full-d --build-dir /tmp/hybrid-d --report /tmp/hybrid-a.json --runs 15 --seed 8681
python3 experiments/track-d-capped-hybrid/compare.py --data /path/to/full-d --build-dir /tmp/hybrid-d --report /tmp/hybrid-b.json --runs 15 --seed 26461
```

Run Linux x86 forced-exhaustion and fallback-heavy memory stress separately and measure cgroup memory; even those observations do not alone establish an all-input proof. No Docker was run on the Mac.

Parent-run native x86 dot VM full-seed comparisons measured the hybrid 15.0–17.7% faster than selected packed u64 and 4.8–7.8% slower than uncapped u32. Across packages 252 full hashes, 24 alternate references, guarded/property and graph-oracle checks passed. Instrumentation reported zero default-pool exhaustion and five wide-state allocations on public seed 1; a separate broad-frontier stress naturally exhausted the default pool 80 times and remained correct. On 12-worker fallback stress, hybrid, u32 and packed process RSS were approximately 927, 553 and 362 MiB respectively. These native VM numbers are not official parent-cgroup peaks, nor do finite stress tests prove worst-case 8 GiB compliance. The conditional memory accounting above remains a significant limitation.
