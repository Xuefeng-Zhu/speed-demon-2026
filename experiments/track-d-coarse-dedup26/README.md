# Coarse-bucket pending deduplication (unselected)

The isolated candidate attempts to avoid duplicate queue entries for the same vertex, side and coarse distance bucket. A separate `pending` array identifies the queued bucket; within-bucket decreases update the exact distance without a second insertion, and a live pop reads the latest exact distance. Entries from displaced higher buckets are stale. Every decrease after a pop re-enqueues. The original fixed pool and exact wide fallback remain. The baseline is exact selected coarse source SHA-256 `2a2a325a1c87e4bc68c260e0d80353e0b8f1f9a7b5be81b1ffeaaede6d813f9d`; candidate SHA-256 `5a4be2f4c80bba1ace634b3abc8982ccc849e81a651726d5730dcedefcc7cb93`.

An independent static review found no concrete correctness defect under single-thread-per-search and nonnegative weights: distances never increase, so a displaced higher-bucket stale entry cannot masquerade as a later live entry; a live bucket pop reads the latest distance and every later strict improvement requeues. Pool failure clears touched distances and pending markers before exact-wide rerun. The marker uses `bucket+1` and fits in u32 because the narrow cutoff is below `u32::MAX`. This is a proof sketch, not a full proof. At the official full node count the extra requested marker payload is approximately 159.4 MiB across 12 workers; allocator/cgroup overhead and the existing 8 GiB hidden-input bound are not established.

`python3 experiments/track-d-coarse-dedup26/verify.py` passed seven forced capacities, 16,000 random and 36,864 exhaustive directed graph queries each, distance cutoffs, packed/wide boundaries, max-weight chain and 6,000 repeated/unreachable queries. `adversarial.py` passed ten dense directed graphs with zero-weight and parallel edges, 23,040 all-pairs queries at each of three capacities, with 3,300,320 repeat expansions and 837,604 inversions instrumented. `long_bucket.py` passed an 8,191-node same-bucket zero-cycle graph and observed pool-exhaustion reruns at capacities 2 and 16. These finite checks do not prove all-input correctness.

One shared ARM native 11-pair full-seed screen plus warmups produced the published hash in all 24 runs. Candidate median wall 0.625269 s versus baseline 0.355785 s (75.7% slower), CPU 2.978323 vs 1.863292 s (59.8% higher), maximum process RSS 723,206,144 versus 585,449,472 bytes. Raw observations and compiler flags are in `arm-screen.json`. This is a shared-host ARM screen, not x86, cgroup, or official measurement, but the large regression does not justify further target testing. The candidate remains unselected; no Docker was run on the Mac.
