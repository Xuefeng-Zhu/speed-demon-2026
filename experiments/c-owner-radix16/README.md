# C radix-sorted owner events (unselected)

`baseline.rs` is the selected dynamic-owner source, SHA-256 `bcd4d7715bffd8a3dc062cad6e7aa0886a96d659fcc9170735c4d4d123f67eae`; `candidate.rs` is `10e1ac47a549006d8908ad69e3ac6580a45b81a793bb476cebabcd64b8257798`. The prototype copies each owner bucket's events into a contiguous vector and stable-sorts them by the low 16 bits of their existing full prehash with two 8-bit LSD radix passes. The full prehash still chooses the owner, so equal names arrive at the same owner. A low-16 run containing one exact byte string uses one reusable group bitset; a run containing distinct strings falls back to an independently randomized exact-byte dictionary with per-name group bits. The packed-name reconstruction and pre-output large-file/group fallback are unchanged. Equal full hashes still concentrate work in one owner, and pathological low-16 collisions can grow the exact fallback map; randomized hashing is not a strict worst-case work guarantee. This is an isolated experiment, not selected source.

On macOS ARM, `experiments/c-rowcache-dynamicparts/reference.py --source experiments/c-owner-radix16/candidate.rs --seeds 24` passed 120 mixed-reference comparisons. Replacing the parser prehash with zero passed another 40 comparisons (eight corpora, five worker counts), exercising a single colliding run and exact fallback. `python3 experiments/c-owner-radix16/edge.py` passed 20 long-name, sentinel, forced collision and forced-fallback comparisons. `python3 experiments/c-owner-radix16/run-property.py` passed stable-order checks from zero through 65,536 events and exact distinct group counts for seven group sizes through 513, with deliberately many different names sharing three low-16 keys. Compiling the exact candidate under overflow and debug checks succeeded. The removed owner dictionary remains dead code in this prototype and produces Rust warnings; do not treat it as final submission code.

One randomized nine-pair full public seed-1 screen after a warmup produced the official output SHA-256 on all 20 executions. Median candidate/baseline wall was `0.070400/0.067103 s` (~4.9% slower), CPU `0.437425/0.423476 s` (~3.3% higher), and native peak RSS was roughly 326/298 MB. Raw observations are in `arm-screen.json`. These are shared native ARM observations, not x86, official scoring or cgroup measurements. The measured regression and extra scratch memory do not justify a target trial; no independent review, full >4 GiB parse, Linux AVX2 or cgroup validation was performed. The public generated input used for the screen was removed. No Mac Docker was used.
