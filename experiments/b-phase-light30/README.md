# Track B lightweight phase diagnostic — not a speed candidate

`baseline.rs` is byte-identical to the selected B source at preparation (SHA-256 `7d371fe84ce9f0fd9d3c7e6fdf02b6b37e0f1440319c654161b990cf27bb8bf3`). `profile.rs` is `5b14befe5ab426451313a512d53d2a37e9b5036e10f56529f4ee337ffdc1f4f9`: it inserts wall-clock timers around existing whole phases and one scan/total pair per indexing worker. It removes the earlier diagnostic's per-query-block prints. It does not alter query or output logic. `generator.py` and `reference.py` are byte-identical copies of the published generator and reference. No dataset, cached answer, credentials or binary is supplied.

This measures **instrumented** wall phases only. Timers, stderr locks, altered inlining and scheduling can change both timings and code generated by PGO. Worker elapsed times overlap and their sum is not CPU time. The PGO procedure below trains `profile.rs` itself; its generated profile differs from that of the uninstrumented selected binary. These results are not official scores, clean performance comparisons, hidden-data guarantees, or parent-cgroup measurements. Optional uninstrumented sampling may help only if `perf` already works; do not change sysctls, mount cgroups, install privileged tools or bypass permissions.

One non-PGO macOS ARM build compiled and ran one warmup plus one measured full-seed run; each output matched the published hash and diagnostic parser accepted all expected phase/worker records. That brief run checks wiring only; its timing is not a performance result. No Mac Docker, actual x86 execution or PGO build was performed.

## Build a self-trained diagnostic on the dot VM

On an idle Linux x86-64-v3 VM with Rust 1.99.1, its matching `llvm-profdata`, Python 3.13, and the published full seed-1 data already present, run the following from this directory. Base images, credentials and data are not included, and no Docker is needed. `build-pgo.sh` checks CPU flags and compiler version, creates its own private `/tmp` directory, generates seed-2 sample data inside it, builds and trains the instrumented diagnostic, checks training output against the organizer reference, merges only fresh raw profiles, then recompiles the *same* `profile.rs` with `profile-use`. It retains that private work directory for inspection and prints its path; remove only that task-created directory when finished, if desired.

```sh
bash build-pgo.sh
# Read the printed work directory and inspect rust-version.txt, profdata-version.txt,
# profile-summary.txt and profile-use-build.log. Confirm matching LLVM versions,
# nonzero profile counts, and no profile mismatch or missing hot-function warnings.
python3 run.py --binary /path/from/build/diagnostic-pgo \
  --data /path/to/verified-full-seed-1 --runs 10 --report /tmp/sd-b-phase-light30-report.json
```

`run.py` performs one warmup and the requested measured runs serially, checks the published output SHA-256 on **every** run, parses all expected phase and worker records and saves per-run observations. Record CPU model, available threads, compiler/toolchain, actual build warnings and complete JSON. Compare phase proportions within this instrumented workload; do not add overlapping thread wall times as CPU, or present the diagnostic's wall time as an official or uninstrumented PGO score. Seed 2 is a separately generated training seed; the unknown holdout seed is not accessed or inferred. For a no-PGO sanity build, use the same flags in `build-pgo.sh` without `-Cprofile-generate` or `-Cprofile-use` and run the same hash-checking driver.
