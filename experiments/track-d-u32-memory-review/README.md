# D u32 cutoff memory review

Reviewed source: `../track-d-u32-cutoff-rebased/candidate.rs`, SHA-256 `5c07ea85035e37157f77c66ccd06d86cefd022cc42311aa95497f78dc4a6d451`. The candidate is experimental and unselected. This is an allocation analysis, not a measurement or a proof that any input exceeds the limit. The full specification gives n=1,740,512, m=5,000,000 and 2,000 queries. Calculations below use 12 worker threads as a scenario; the executable actually calls `available_parallelism()`. Memory is 64-bit Linux unless stated otherwise, and additional allocator, cgroup/page-cache, container and stack costs are excluded unless mentioned.

## Fixed payloads

* The packed forward and reverse CSRs each reserve `4*(n+1) + 8*m` bytes, or 93,924,104 bytes total (~89.6 MiB). The compact and wide arrays each reserve four bytes per edge; the wide array is not absent. Untouched zero pages may not be physically charged, depending on allocator and Linux behavior.
* Each worker's narrow distance vector reserves `8*n` bytes. If all 12 workers have ever fallen back and retain their lazy wide state, narrow plus wide distance vectors reserve `24*n*12 = 501,267,456` bytes (~478.1 MiB), versus `16*n*12 = 334,178,304` bytes (~318.7 MiB) for a wide-only distance vector. This excludes all touched vectors, queues and graph memory. The 167,089,152-byte difference is an allocation comparison; actual cgroup charge depends on pages touched and allocation reuse.
* A touched vector can contain at most n distinct node indices in one query. Twelve such vectors at length n contain 83,544,576 bytes (~79.7 MiB) per search state, before vector capacity slack; both retained search states have separate touched vectors. `Vec` growth may reserve more than length.
* The input graph has at most 27 bytes per edge line from the numeric ranges, or roughly 135 MB plus its short header. Positioned-read buffers sum to about the input file size, plus split overlap. Prewarmed file cache, buffers, allocator-retained memory, forward/reverse bucket vectors, temporary reallocations, CSR arrays and builder cursor vectors can overlap at loading peaks. They must not be added blindly to query-state payloads because phases differ, but their cgroup pages may persist.

## Heap retention and the missing upper bound

Each worker has two radix heaps in `Search32`; after a wide fallback, the retained `Option<Search>` adds two more. On 64-bit target builds, each `(u64,u32)` heap tuple normally occupies 16 bytes. All 65 bucket vectors preserve their allocations when `RadixHeap::clear()` invokes `Vec::clear()`, and `top()` puts the drained bucket vector back, so retained capacity can be accumulated across different buckets and queries. The narrow and wide search states are both retained after a fallback. Peak cgroup memory is therefore not bounded by just the distance arrays, one query's live heap entries, or the process RSS observed on the seed-1 sample.

For one side of a shortest-path search, each vertex is settled at most once with the best key; at most m successful edge-relaxation insertions plus the source are possible. A deliberately loose envelope takes each bucket independently as having reached m+1 live entries in some query and allows geometric `Vec` capacity below roughly twice its maximum length. Narrow keys use at most 33 buckets; all tentative wide keys are below 2^53 under the full graph bounds, so at most 54 buckets are used. Multiplying that loose envelope by two sides, both search states, 12 workers and 16 bytes per tuple yields hundreds of GiB, well above 8 GB. It overcounts heavily and does **not** demonstrate a realizable official input or predict actual allocation, but it demonstrates that the simple per-query and fixed-array counts do not certify the 8 GB limit. Allocator growth transients further complicate a strict bound. The generated road-network and query-rank structure may tighten this envelope, but no proof using those guarantees is supplied here.

The same original packed implementation already retains radix heap capacities; the u32 candidate adds a second set of heaps and distance/touched arrays on workers that encounter a fallback. On official full data the number of fallback-triggering queries and schedule of workers affect whether all 12 wide states are instantiated. Neither a nominal process RSS number nor a synthetic run alone proves all valid seeds safe. Parent-run full x86 cgroup and deliberately fallback-heavy stress testing is appropriate evidence, but still not a universal proof.

## Possible mitigations, not implemented

For a rare fallback, free the cleared narrow heap vectors before invoking the wide search, and drop the wide `Search` immediately after it finishes. That reduces concurrently retained application allocations and stops wide state persisting across later queries; it also reallocates on every fallback and might hurt speed. It does not by itself establish an 8 GB cgroup bound, since one query can retain a range of radix bucket capacities and allocator pages may remain charged. An explicit per-worker memory budget with a bounded-memory exact fallback (for example an indexed decrease-key heap with one entry per vertex per side) plus careful allocator/cgroup accounting would be a stronger design, but needs a correctness proof, implementation, tests and target speed measurements. Limiting worker count can also help, at an explicit throughput cost, but alone does not prove a bound while the sum of retained bucket capacities remains uncontrolled.
