# Opposite-frontier pruning (unproven experiment, not selected)

After a finite best path exists, the candidate attempts to prune a relaxation using the other heap's minimum and, when present, the other side's tentative distance. The source is derived from positioned-read Track D. **Correctness is unresolved:** once both directions prune, a previously pruned opposite vertex may be undiscovered despite a true distance below the current opposite minimum. Passing tests do not establish a repaired mutual-pruning invariant. Do not use or promote this candidate without a rigorous proof and adversarial review.

Overflow/debug-checked tests passed 16,000 random queries, 36,864 exhaustive three-node queries, 376 directed chain/cycle fixtures, the maximum-size maximum-weight chain and 6,000 repeated/unreachable queries; all full-seed hashes matched. Nine shared ARM native pairs (`report.json`) had median 0.28344 s vs 0.27134 s baseline, CPU 1.86260 vs 1.83254 s, max native RSS 534,298,624 vs 534,773,760 B. One instrumented full-seed run (`profile.rs`, `profile.txt`) counted 1,314,188 skips among 21,026,528 candidate relaxations; instrumentation is not timing evidence. This slower result is not target x86 or official cgroup data. No Mac Docker was used.
