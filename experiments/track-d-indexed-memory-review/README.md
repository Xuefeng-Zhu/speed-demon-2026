# Indexed-radix D memory accounting (conditional; unselected)

Candidate reviewed: `../track-d-indexed-radix/candidate.rs`, SHA-256 `5e0caa893af2ae87c65cbb696f902c89c2c8fe30b06d97bfd4e220eedeed885c`. This is an allocation-accounting analysis, not a claim that the executable always stays under its cgroup limit. The fixed `full` contract is `n=1,740,512`, `m=5,000,000`, `q=2,000`; the candidate caps each scoped worker phase at 12 threads. It is unselected after its native sample speed screen. No Mac Docker was run.

## Fixed application payloads

An indexed radix heap preallocates one `[u32;2]` link per vertex and has fixed 65 bucket heads. It allocates nothing on push, remove, top, redistribution or clear. `Search32` requests `8n` bytes for distances, `4n` for its touched list, and `16n` for two heap link arrays: `28n` bytes per worker. Wide `Search` requests `16n+4n+16n=36n`; a fallback worker retains both. If all 12 workers have instantiated both states, their requested search-array payload is `64*n*12 = 1,336,713,216` bytes (about 1,274.79 MiB). This includes the worst number of queued vertices regardless of the number or distribution of edge relaxations. The touched lists contain at most n distinct vertices per search, so they do not need to grow beyond their initial requested capacity. The two full packed CSR graphs request `2*(4*(n+1)+4*m+4*m) = 93,924,104` bytes. Each graph still requests 8m bytes for compact and wide per-edge arrays together.

The linked heaps have fixed bucket-head arrays, Vec headers, count and last fields; these and thread handle/control structures are small relative to the arrays, but must be included in a formal bound. The full graph input has at most 7+1+7+1+10+1=27 bytes per edge and a 16-byte header, hence at most 135,000,016 bytes. The query file has at most 16 bytes per query, or 32,000 bytes. A shortest finite path is bounded by `(n-1)*(2^32-1)`, at most 16 decimal digits; output is at most 34,000 bytes. The file page-cache footprint attributable to graph, queries and output cannot exceed their contents rounded up to cache pages, but which cgroup owns cached pages and additional file/kernel charges depends on the official harness and kernel; this is not established merely from file sizes.

## Loader vectors and input buffers

There are 2 directions × t parser threads × t target blocks. Each bucket initially requests `c = floor(floor(m/t)/t)*9/8 + 64` Edge slots. `Edge` is a tuple of three u32s (12 bytes on the target ABI; its size is not explicitly asserted in this candidate). Across both directions exactly `2m` edge records are pushed. At t=12, the 288 buckets request an initial 11,268,288 slots (135,219,456 bytes); for integer t from 1 through 12 this is the largest initial sum.

**Conditional estimate, not Rust API guarantee:** if the pinned target Vec implementation doubles capacity on push without additional exposed capacity, a bucket of final length L has capacity less than `c + 2L`. Therefore final requested bucket storage is at most `12*(2*t*t*c + 4m)`, at most 375,219,456 bytes at t=12. If a growth realloc simultaneously keeps both the old and new buffers, and old capacity is no more than half the new capacity, an additional half of the new-capacity bound gives 562,829,184 bytes for the bucket payload plus transient copies. The implementation and allocator can round, hold old arenas after free, or expose capacity in ways not bounded by the `Vec` API; this 562.8 MB is therefore a conditional application-requested payload estimate, not a cgroup peak guarantee. Only an explicit allocator/growth contract or code-enforced fixed allocations can turn this into a portable hard bound.

Each positioned input buffer includes its assigned byte interval, a preceding byte, and at most 32 following bytes. Across all t buffers the requested bytes are at most `file_len - 1 + 33t`, or 135,000,411 bytes for t=12. Concurrent CSR-building cursors together request at most `4n` bytes; both complete CSRs request the 93,924,104 bytes above. Loader bucket vectors, input buffers, cursors, and CSRs do not all logically peak simultaneously, but freed anonymous pages/arenas and cgroup page cache can persist into later phases. A conservative planning estimate can add them all, but doing so still does not bound allocator or kernel overhead.

## Remaining blockers to an 8 GB proof

* `Vec::with_capacity`/`vec!` request sizes are specified in source, but Rust does not promise a universal upper capacity, growth factor or allocator retention. The loaded tuple size is an ABI fact, not an asserted source invariant. A target-specific proof needs the exact pinned Rust and allocator implementation, or explicit fixed-size allocations with known accounting.
* Thread-stack sizes and retention are not fixed explicitly by the code; they can depend on the runtime and environment. Threads are spawned in multiple phases, although at most 12 scoped workers run in each phase. The exact harness environment, `RUST_MIN_STACK`, libc and Linux stack caching policies must be bounded or replaced with explicitly sized stacks.
* Cgroup peak can include anonymous memory, file/tmpfs cache, allocator arenas and fragmentation, shared runtime/image pages and kernel charges. The available local `check.py` shows an 8g Docker limit but does not specify a formal maximum for all such charges or an exact cache ownership policy. The pinned runtime image and kernel/cgroup configuration must be established and accounted for. Counting only process RSS or a VM stress observation is insufficient.
* Fixed-size queue payload proves an algorithmic queue bound, contingent on correctness of its one-entry-per-vertex and touched-once invariants. It does not prove the complete container peak. Correctness, x86 and official performance must also be verified independently; the prototype was slower on its ARM sample.

A conservative policy is to keep the current selected source until a competitive candidate has both adequate target performance and a defensible cgroup envelope. None of the calculations above establish that any valid seed exceeds 8 GiB, nor guarantee that every seed stays below it.
