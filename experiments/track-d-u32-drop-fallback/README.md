# D u32 fallback state-release experiment (unselected)

`baseline.rs` is the exact experimental u32 cutoff candidate SHA-256 `5c07ea85035e37157f77c66ccd06d86cefd022cc42311aa95497f78dc4a6d451`, not the selected competition source. `candidate.rs` SHA-256 `e5bf8630fc13fc38600aece44c223f634f98c78b3c8e39c00b3176d8b246fab9` changes only fallback ownership: it drops all narrow search state before constructing the wide `Search`, drops the wide state immediately after it finishes, and constructs fresh narrow state for later queries. This avoids simultaneously application-owned narrow and wide search states in one worker, but allocator retention and cgroup charge can persist. No selected source was modified.

**Not a memory-safety proof:** a single search retains capacities in as many as 54 wide radix buckets per side across queries. With m=5,000,000, a deliberately loose envelope of at most m+1 live insertions per side and geometric Vec capacities below approximately twice each bucket's maximum gives roughly `54 * 2 * (m+1) * 16 = 8.64 GB` for one wide side before realloc transients, other heaps, graph and allocator/page-cache overhead. This does not construct a reachable valid holdout failure; it shows that this conservative accounting cannot certify the limit. Generated road-network/query-rank constraints may sharpen it, but no full proof is provided. The release change alone therefore cannot be called safe under all valid holdout inputs. For detailed context see `experiments/track-d-u32-memory-review/README.md`.

Debug and overflow-checked native ARM build passed: cutoff minus one, cutoff and cutoff plus one; zero, self and unreachable; 16,000 randomized independent Dijkstra queries; 36,864 all-pairs queries across 4,096 directed graphs; a full-size maximum-weight chain; and 6,000 repeated/unreachable queries. These exercise fallback and state recreation but not every schedule.

Two randomized 15-pair native ARM runs on public sample seed 1 matched the published output hash in all 64 executions. In `sample-arm.json`, retained/release median wall was `0.0185761 / 0.0198609 s`, CPU `0.091354 / 0.093402 s`, max process RSS `37,912,576 / 41,222,144 B`. In `sample-arm-repeat.json`, retained/release wall was `0.0192664 / 0.0192524 s`, CPU `0.089617 / 0.090311 s`, max RSS `37,748,736 / 41,435,136 B`. These small shared-host timings are not full-scale, x86, cgroup or official measurements.

A deliberately **non-holdout synthetic** stress repeats the three actual fallback-triggering sample-seed-1 queries (indices 9, 31, 158, confirmed by an instrumented run) to make 2,000 queries. Nine randomized ARM pairs and warmups all matched independently reconstructed output SHA-256 `0d05b38657900e99f9c4c5e96a5a570d76010c08caf5611cb13690c00f2124fe`. In `fallback-heavy-arm.json`, retained/release median wall was `0.00781725 / 0.07276263 s`, CPU `0.028898 / 0.462053 s`, max process RSS `32,423,936 / 52,346,880 B`. Recreating state every fallback caused a severe local slowdown and no RSS improvement in this scenario. It does not measure the official generated query mix or establish x86 behavior. The prototype is not recommended for promotion on the evidence available.

To recreate this stress, generate the official sample seed 1, compile the baseline, run it on the sample and confirm its output SHA-256 is `a4c76ed030bc7e365db33191f6cf74708fba7f25eb48d64c8c4279f2e57046a0`; then run `python3 experiments/track-d-u32-drop-fallback/prepare-stress.py /path/to/sample /path/to/verified/distances.txt /path/to/new/stress-dir`. The target directory must not exist and be on the same filesystem as the sample for the hard link. Use `compare.py` with that directory and the expected digest above. The repository contains neither datasets nor generated answers.
