# Independent A two-lane parser review

Reviewed candidate `../a-two-lane-interleaved/candidate.rs`, SHA-256 `b98d76ca3d17b959c43c01c33c227d9614196710d4733a68be1b03829c560b0c`, against selected baseline SHA-256 `4af40353f517f566217b0f882ec25d8002f61d211dcc479c53f8a1dd5de7ed88`. This is an isolated review, not a selected change or a performance measurement.

The unchanged outer cuts create newline-aligned, disjoint chunks. Within one chunk, the midpoint moves forward to immediately after an LF or the end. The two resulting half-open intervals cover the chunk once, including empty or collapsed halves. The paired loop advances each live cursor by one complete record; each sequential tail consumes its remaining interval. Both lanes share only their worker-local table, and its lookups are sequential: a different first-appearance order changes local IDs but not the exact bytes used to construct global sorted ranks. For each hour, compact markers and their escape payloads are appended in the same order, so changed input order leaves the decoded record multiset, grouped percentile inputs, and error counts intact. Under the official grammar, timestamps and endpoints contain no textual escape sequences; the compact-record escape encoding still requires testing. On the 64-bit target, official row and endpoint limits keep ID, count, rank, and hour arithmetic in range.

`python3 experiments/a-two-lane-independent/run.py` verifies the exact candidate hash and compiles four temporary test builds. Its independent synthetic oracle decodes each `Chunk` to exact `(hour, endpoint bytes, latency, error)` records, checks every compact marker consumes exactly one matching escape payload, and compares sorted record multisets. It exercises all **2,145** contiguous line-aligned subranges of a 64-record mixed corpus and **209** subranges of a 2,500-record corpus with **2,155 distinct endpoints**, including more than 2,048 IDs. Inputs vary across all methods, all 72 hours in non-time order, endpoint lengths 1 and 125, repeats, 499/500/599 statuses, and latencies at and around the compact limit and `u32::MAX`.

The unchanged candidate source with release-style `overflow-checks=no` passed the property normally and with a temporary forced-zero table hash. Two more debug/overflow-checked test builds also passed after **test-only** substitution of explicit wrapping operations for the three unchanged SWAR operations in `parse_latency`; this is equivalent to the normal optimized release arithmetic. An earlier test build with unmodified source and `overflow-checks=yes` panicked in the unchanged baseline's SWAR multiply at line 86. Consequently this review does **not** claim the unmodified baseline or candidate works with overflow checking enabled. The source files were not altered by these test-only substitutions. The Cargo Dockerfile builds the release profile; actual x86, official cgroup performance and hidden-data correctness remain unverified.
