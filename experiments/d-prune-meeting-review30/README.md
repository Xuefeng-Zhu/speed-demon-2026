# Forward-prune meeting branch regression

This independent regression targets candidate SHA-256 `c33d3984871fb22ed7c2d678b3a3562ac82d46cb952a8a0461980301c5a553ef` from `track-d-coarse-forward-prune29`. It operates only on temporary instrumented copies and leaves selected code untouched.

`python3 experiments/d-prune-meeting-review30/targeted.py` compiles overflow-checked, debug-asserted copies with forced pool capacities 0, 1, 2, 16, and 65,536. It compares both the candidate and an experimental mutant that omits the before-prune meeting update with an independent Bellman–Ford oracle. The eight-edge directed fixture uses legal uint32 weights and forces an actual meeting improvement before pruning at the default cap; the candidate's exact wide rerun produces 5,000,000,065. Small forced caps exercise fallback without requiring the improvement branch. The script also checks a zero-weight self-loop/parallel-edge variant. The mutant is diagnostic only, not proposed for competition.

The script passed all ten instrumented configurations (two code variants × five caps) and both fixture variants. At caps 16 and 65,536, the actual candidate recorded one before-prune improvement and returned the intermediate narrow result `5,000,000,065`; the mutant recorded the same opportunity but left the intermediate result at `7,500,000,000`. Both set the cutoff flag and the exact wide rerun matched the independent oracle at `5,000,000,065`. At caps 0, 1 and 2 both variants requested exact fallback and matched the oracle. No before-prune improvement below the cutoff was observed in this fixture.

`python3 experiments/d-prune-meeting-review30/search.py` reproduces a deterministic search over two million small directed multigraphs and ten million queries, using weights including zero, 63/64/65, very large weights and `u32::MAX`. It passed with 206 queries having at least one meeting improvement before pruning, but none where the improving candidate itself was less than `u32::MAX`. Separately, a narrow final answer was seen after an earlier above-cutoff improvement; a narrow final answer alone therefore does not establish a narrow improvement. This finite search does not prove unreachability.

An argument for why a below-cutoff improvement is unreachable under the implementation invariants: if the reverse label at destination `v` is below the reverse pending bucket start `b`, reverse expansion at that label has already relaxed the reverse edge from `v` to forward predecessor `u`. If `d_f(u) + w(u,v) + d_b(v) < u32::MAX`, that reverse relaxation cannot have been discarded at the narrow cutoff. The resulting reverse label at `u` is no greater than `w + d_b(v)`. Whenever the later of the current forward or reverse labels at `u` was installed, the implementation already considered their meeting, so `best` is no larger than that candidate. This relies on nonnegative weights, complete lower-bucket drainage, no exhaustion (otherwise exact wide rerun), and the actual current forward label being the popped non-stale value. It is a review argument rather than a machine-checked proof; keep the explicit before-prune update.
