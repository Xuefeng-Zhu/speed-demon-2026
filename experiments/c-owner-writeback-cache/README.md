# Owner cache with inline write-back group bits (unselected)

`baseline.rs` is the exact selected two-lane/dynamic-owner C source, SHA-256 `8249f318e26050cc1a12f2be091344bf431ceb862665a3312bb29a92e140057d`. `candidate.rs` SHA-256 is `012e45158b45945241711f133f0d0f81f992ea1bd3a1eacfcebfdf89e9dc33b1`. Neither selected code nor any remote branch was changed.

For at most four group words, the direct-mapped owner cache stores each cached exact name, full hash, stable row and four group words together. A hit checks hash and full name bytes before updating the cached word. On replacement it writes that row's bits back into the authoritative vector, then loads the next row. Same-name routing to the same owner and cache slot follows from deterministic full hashing. No flush at dictionary drop is needed because distinct counts are accumulated on every event; replacement flushes are required before any row can be revisited. More than four group words use the original exact dictionary/bit-vector path without the cache. The input/owner routing and file/group-limit fallback remain unchanged.

This increases each cache slot from 16 to 64 bytes on a 64-bit ABI, or approximately 18 MiB more requested payload across twelve simultaneous owners; temporary allocator peaks and actual cgroup usage were not measured. The experiment passed `python3 experiments/c-owner-writeback-cache/property.py`, a debug/overflow-checked eight-million-operation replacement, promotion and group-boundary model at 1/63/64/65/240/241/256/257 groups; `python3 experiments/c-owner-writeback-cache/reference.py --source experiments/c-owner-writeback-cache/candidate.rs --seeds 24` (120 mixed official-reference comparisons); and `python3 experiments/c-owner-writeback-cache/forced-collision.py` (actual three parser hash sites forced equal, promotion and long sentinel at five worker counts). These finite tests are not an all-input proof. The implementation has not received independent review, actual x86 SIMD/guard-page tests, full >4 GiB parsing, or official cgroup measurement.

In a single serialized native macOS ARM full public seed-1 screen of seven randomized pairs after warmup, all 16 output hashes matched. Median wall was 0.067953 s candidate vs 0.063463 s baseline (7.1% slower), median CPU 0.406913 vs 0.398321 s, and native process RSS was approximately 313 vs 294 MB. `arm-screen.json` contains each observation. The pre-existing `/tmp/sdc-full` input hashes were checked against the official spec and were not changed or removed. Native ARM wall/RSS are not Linux x86 or official scoring/cgroup metrics. This preliminary screen shows a regression, so the candidate remains unselected and is not recommended for a target slot without new evidence. No Mac Docker was run.
