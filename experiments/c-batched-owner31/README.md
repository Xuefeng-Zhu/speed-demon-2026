# Four-event owner cache snapshots — unselected

Baseline is exact selected C source SHA-256 `8249f318e26050cc1a12f2be091344bf431ceb862665a3312bb29a92e140057d`; candidate SHA-256 `4488d74d308803714c9ac42a457d03c8fbeab2e53e57c015d6d99d0b44997933`. Each exclusive owner processes batches of at most four events. It snapshots hash-matched direct-cache row indices and names, checks exact name bytes in a second pass, then applies all group-bit mutations in original order. Misses use the original exact `see`. A validated snapshot row remains a valid exact name after an earlier batch event evicts its cache slot or causes vector growth/promotion because entries are append-only and row IDs stable. Reinstalling the exact hit into the slot preserves correct results; exact bytes are always compared. Routing, collision promotion and the original file/group fallback are unchanged. This was a memory-level parallelism hypothesis, not a target-speed claim.

Independent static review found no concrete defect under the existing valid-input and append-only-row invariants. `python3 experiments/c-batched-owner31/property.py` compiles an optimized debug-asserted/overflow-checked exact candidate and compares batched result to scalar `see` and an independent `HashSet` after each batch across 648,081 events. It covers direct-slot A/B/A conflicts, first-time repeated names, full-hash collision and promotion, empty names, a 65,536-byte sentinel name, quoted escaped bytes, 1/63/64/65/240/241/256/257/513 groups and short final batches. `python3 experiments/c-fused-namehash/reference.py --source experiments/c-batched-owner31/candidate.rs --seeds 24` passed 24 mixed CSV corpora across five worker counts (120 reference comparisons). These finite tests do not prove hidden-data correctness or the 8 GiB cgroup bound.

After a coordinated native macOS ARM handoff, both sources were compiled with `rustc --edition=2021 -O -C lto=fat -C codegen-units=1 -C panic=abort`. `experiments/c-rowcache-dynamicparts/compare.py` ran warmed randomized pairs on full public seed 1. Nine-pair candidate/baseline median wall was `0.065046/0.065265 s`, CPU `0.402062/0.395927 s`; fifteen-pair repeat was `0.064819/0.064716 s`, CPU `0.399866/0.396952 s`. All 52 warmup/timed full outputs matched the published hash. `arm-screen.json` and `arm-repeat.json` preserve raw values. Shared-host ARM wall was effectively tied and CPU was 0.7–1.5% higher; no substantial win is demonstrated. The candidate remains unselected; no x86, guard-page, full >4 GiB, or official cgroup test was performed. No Mac Docker was run.
