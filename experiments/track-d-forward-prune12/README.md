# Forward-only opposite-frontier pruning (unselected experiment)

This experiment starts from the exact selected bounded hybrid source (`baseline.rs` SHA-256 `671c639be3400209e83e080dfb54947affd30ca71dc34ec17804d24d70292d9c`). Its candidate changes only narrow forward relaxations after a finite complete-path upper bound exists; backward narrow search is not pruned. A candidate with `nd + b >= best`, where `b` is the current backward heap minimum, first updates `best` using any known backward path at its destination, then skips inserting that forward relaxation. The original numeric-cutoff flag, pool exhaustion cleanup, exact indexed-wide fallback and worker cap are retained.

Proof sketch requiring independent review: all edge weights are nonnegative, and each known tentative distance denotes a real path. For a skipped candidate path to `v`, if the true reverse distance from `v` to the target is at least `b`, the combined path is not better than `best`. If that distance is strictly below `b`, reverse Dijkstra—whose relaxations are never pruned—has settled `v`; its stored reverse distance is exact and the meeting check above has already considered that path. Stale reverse heap entries can only decrease `b` and make pruning more conservative. The narrow cutoff does not break the less-than-`b` argument: `b` is itself below `u32::MAX`, so every prefix of a reverse path shorter than `b` is also below that cutoff. Discarded forward candidates remain unable to improve later best values as reverse minima advance and best only decreases. The argument must be checked for all termination and empty-heap cases, and pool exhaustion still forces the unmodified wide rerun.

This is unselected and unsubmitted. Correctness, independent proof, target x86 speed, cgroup memory and hidden-data behavior are not established by this note. Do not infer a speedup; a prior symmetric pruning attempt was slower and lacked the one-sided invariant. No Docker on the Mac.

Independent static review found no concrete counterexample under the stated invariants. The independent exact-SHA test in `../track-d-forward-prune-independent/` ran 4,096 exhaustive three-node graphs and 12,000 deterministic random 2–8-node directed multigraphs per capacity (0/1/2/65,536), including zero/cutoff/u32-max weights, repeated edges, all-pairs Floyd–Warshall comparisons and state cleanup. At default cap it observed 63,704 prunes: 7,637 reverse-known labels below b, 16,316 reverse-known labels at or above b, 39,751 reverse-unseen labels, and 42,526 with b=0. It observed one case where meeting-before-prune strictly improved best, 4,832 forward-empty and 21 reverse-empty exits after pruning, and 159,500 cutoff events; cap 2 also exercised 53,289 exact pool-exhaustion reruns. These are finite tests, not a formal proof of all hidden inputs or cgroup memory.

The standard debug/overflow `verify.py --extremes` suite passed capacities 0/1/2/65,536, forced pool cleanup, a million-operation queue model, 16,000 random graph answers and 36,864 exhaustive answers per build, cutoff-1/cutoff/cutoff+1, packed node boundaries, the full-size max-weight chain and 6,000 repeated/unreachable queries. Candidate SHA-256 is `8aafe3a1d1e18e9d3bc0cf8a96fd5d1316023df2f5691e06feb74be6771eac16`.

Native shared ARM full seed-1 screens used randomized pairs and checked every output hash. Seven measured pairs gave candidate 0.272347 s versus baseline 0.275803 s, with CPU 1.840962 versus 1.824955 s; a separate clean 15-pair repeat gave 0.251105 versus 0.249895 s, CPU 1.815785 versus 1.815665 s. An unrelated <0.1-second Python compile occurred at 12:17:26 UTC and may have overlapped the first screen, so do not treat that batch as clean. All 48 outputs including warmups matched the published full hash. Raw observations are `arm-first.json` and `arm-repeat.json`. There is no stable speed win, no Linux x86 or official cgroup result, and no target recommendation. The candidate remains unselected.
