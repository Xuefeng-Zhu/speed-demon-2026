# One-sided forward-pruning independent review

This review concerns the isolated candidate `../track-d-forward-prune12/candidate.rs` (SHA-256 `8aafe3a1d1e18e9d3bc0cf8a96fd5d1316023df2f5691e06feb74be6771eac16`), not the selected program. The candidate only prunes forward relaxations; the reverse search is not pruned. The original u32 cutoff flag and fixed-pool exhaustion fallback remain in force.

For a forward candidate path of length `nd` to `v`, the candidate prunes only when `nd + b >= best`, with `b` the reverse heap minimum. The tracked best value is always the length of an actual s–t path. If the true reverse distance of `v` is at least `b`, this prefix cannot improve that best. If it is less than `b`, the unpruned reverse search must already have settled `v` with its exact reverse distance. The candidate checks the known reverse label before pruning and incorporates any resulting meeting path into `best`. Since `b < u32::MAX`, a reverse path with distance less than `b` cannot have been removed by the narrow cutoff; zero-weight ties and stale heap entries only make `b` conservative. Thus any pruned prefix cannot produce a path improving the resulting best, which never increases. A future smaller forward path to the same vertex remains eligible for insertion. This supports the ordinary two-frontier termination and the case where pruning empties the forward queue: a path below the returned best cannot have lost an essential prefix to this rule. Pool exhaustion still causes the unchanged exact wide rerun, and cutoff relaxations still set the original `dropped` flag before the new rule runs.

The test script asserts the candidate hash, creates **temporary instrumented copies**, and runs Floyd–Warshall all-pairs checks and state-cleanup assertions for forced pool capacities 0, 1, 2 and 65,536. Instrumentation counts actual pruning against known reverse labels below or at/above the frontier, unseen reverse labels, zero reverse minima, meeting improvements, post-prune heap-empty exits, cutoff events and pool exhaustion. The script does not change the candidate or selected source. Branch counts must be reported as observed; no particular rare branch is assumed reachable.

This static reasoning and finite oracle tests do not independently establish every valid input, Linux x86 performance, parent-cgroup peak, or a formal 8 GiB bound. No Mac Docker is used.

The independent run passed on native ARM in optimized test builds with overflow and debug assertions. Each of capacities 0, 1, 2 and 65,536 ran all pairs on 4,096 exhaustive three-node graphs plus 12,000 deterministic random directed multigraphs with 2–8 nodes, zero and maximum weights, loops and duplicate arcs; all results matched Floyd–Warshall and both states were clean after each query. At default capacity the instrumented source executed 63,704 prunes: 7,637 had a known reverse label below `b`, 16,316 had a known label at least `b`, and 39,751 had no reverse label; 42,526 had `b=0`. The meeting-before-prune update strictly improved `best` once. There were 4,832 forward-empty and 21 reverse-empty exits after a prior prune, plus 159,500 cutoff events. The capacity-2 run also exercised a meeting improvement, both empty-exit cases and 53,289 pool-exhaustion fallbacks. Capacity 0 immediately reruns wide and does not enter the pruning branch. Counts are diagnostic for this corpus, not performance measurements or coverage of all inputs.
