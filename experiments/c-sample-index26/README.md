# C runtime sampled-name index — unselected

The baseline is the selected source SHA-256 `8249f318e26050cc1a12f2be091344bf431ceb862665a3312bb29a92e140057d`. The isolated candidate is SHA-256 `27ed2de9286dbcb210ea4f26aaf2267910c6fcd8b93a6fcebd2054720e2810f7`.

The candidate makes a bounded runtime prepass over up to 16 MiB of records, collecting exact-byte names in a fixed-size immutable table. Each full-pass parser records sample-known names in a private name-by-group bitmap, routes unknown names through the original owner-event reduction, and reducers OR private bits before counting. Sample table construction abandons the approach after 32 probes or 131,072 names; checked logical worker-bitmap allocation is capped at 64 MiB and the original path handles any aborted sample. The prepass uses the organizer's §2.2 CRLF and no-CR-inside-fields guarantees and may skip LF-terminated records; every record is still processed by the full pass. The sample affects optimization only, not the answer. The exact lookup checks complete name bytes; no cached answers or input recognition are used. Actual sample coverage was not instrumented.

A first native shared Mac ARM screen, with matching `rustc --edition=2021 -O -C lto=fat -C codegen-units=1 -C panic=abort` flags, five randomized full-public-seed pairs and one warmup, matched all 12 published output hashes. Median wall baseline/candidate was 0.062998/0.081840 s and CPU 0.399633/0.468873 s, with peak process RSS 298,844,160/267,304,960 bytes. The candidate was approximately 29.9% slower in this preliminary screen. Measurements are native, not official x86 or parent-cgroup data; raw samples are in `arm-screen.json`. An extra initial candidate run also matched the full hash. No Docker was run.

A read-only independent review found no concrete routing, full-byte comparison, conservative fallback or bitmap-union defect under §2.2, but this candidate has not passed alternate-reference, forced-active small-sample, collision, group-boundary, memory-cap, long-name or x86 guard tests. Its checked 64 MiB cap applies only to logical bitmap payload, not total process or cgroup memory. It is a failed preliminary speed experiment, **not a validated submission**, and should not be promoted on these results.

To reproduce the preliminary comparison with an independently generated full seed-1 dataset, compile `baseline.rs` and `candidate.rs` with identical flags above and run `python3 experiments/c-nameowned/compare.py --baseline /path/to/baseline --variant /path/to/candidate --data /path/to/full-c --runs 5 --report /path/to/report.json` without other benchmarks. The report verifies each published output hash and records process RSS, not parent-cgroup peak.
